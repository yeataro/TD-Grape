# 節點定義與註冊表

本文記錄本輪對話已確認的定義引用、登記與初始化關係。能力如何分類及安放、定義內部如何引用行為、產碼契約仍未定案，不從舊文件補入。總覽見[重構計畫入口](README.md)。

## Node 引用節點定義

圖內 Node 引用一份建構完成、可查詢的節點定義物件，目前採用 NodeDefinition 這個名稱。Node 可以查回自己的定義及其名稱；Node 的個別名稱與定義名稱分開辨認。

```ts
node.name;             // 圖內這顆節點的名稱
node.definition;       // 引用的 NodeDefinition
node.definition.name;  // 定義名稱
```

以上片段表達查詢關係，不是現行 API。多顆 Node 可以共用同一份定義，同時保有各自的設定、接口、本地輸入值及連線。定義內的接口規格與某顆 Node 上實際建立的 Input／Output 是不同層次。

NodeDefinition 是共同定義的查詢入口；確認這個關係，不代表已決定每種節點是否各有 class，或普通節點是否全部共用同一種 Node 實作。

## 註冊表與多個提供者

可用定義由註冊表管理，供編輯器新增選單、節點建立流程及查詢使用。註冊表可以接受多個提供者；不同提供者不必使用相同的原始資料格式。

已確認可以包含這幾種來源方式：

- 文件經讀取及建構，產生 NodeDefinition 後登記。
- 程式直接建立定義物件後登記。
- 其他模組已有可用的定義物件，登記其引用，不要求重新複製一份。

註冊表負責管理與查找，提供者負責交付定義。定義可以引用其他共用物件，不要求所有規格與能力都複製進自身。提供者不是圖內供應數值的 Source，兩個概念保持分開。

NodeRegistry 與 NodeProvider 是討論中使用的候選名稱。已確認的是註冊表與提供者的角色；具體類別、方法、初始化入口的簽章及登記錯誤處理仍待細化。

## 先初始化再使用

定義列表必須先經過初始化，再供新增選單及節點建立流程使用。同一批已載入完成的定義可重複查詢及引用，不因每次新增 Node 就重新讀取原始文件、重新建構一批定義。

```text
多個提供者
    ↓ 讀取或建構，亦可交付既有物件
完成並登記的 NodeDefinition 列表
    ├─ 新增節點選單查詢
    ├─ 節點建立流程取得定義
    └─ 圖內 Node 引用定義
```

這裡要分清兩次建立：

| 階段 | 建立什麼 |
| --- | --- |
| 定義初始化 | 可供共同引用的 NodeDefinition，以及可查詢的定義列表 |
| 在圖內新增節點 | 某一顆 Node 及它自己的狀態，引用已準備好的定義 |

載入新提供者或新定義，可以有相應的初始化。註冊表的作用範圍、應用程式何時啟動流程、重新載入、更新及解除登記後如何處理既有 Node，尚未決定。

## Parameter 的基本規格

定義可明確指定某個 Input 是否提供 Parameter。提供時，基本編輯方式可以從 DataType 與接口的樣式取得，再按需要補上範圍、clamp 或樣式等特殊設定；不提供時，仍可建立 Input。

普通節點不必為每個輸入重複描述完整的基本編輯方式，也不因存在 Input 就強制產生 Parameter。這裡確認的是規格來源與選擇能力；描述格式、建立方法及不同層級設定的合併細節另行設計。Parameter 的值歸屬與行為見[接口與接線](TYPES_AND_CONNECTIONS.md)。

## 已確認的設計要求

定義必須能容納模式、動態接口及型別關係等能力，不能只以某個固定配置下的接口清單代表所有節點。Swizzle、Voronoi 在討論中用來說明這個需求，不在本文件固定它們的完整功能或設定值。

能力需要能拆解、重用及組合；先釐清各項能力的責任歸屬、依賴及使用位置，再決定如何安放實作。這是已確認的設計要求，尚不是已完成的能力分類或組合契約。

目前不把 NodeDefinition 上的 resolve、generate 等方法列為正式 API，也不決定它是否直接執行產碼。定義如何提供產碼所需的資訊或能力引用，與產碼系統如何使用它，仍需討論。具體未決項目見[待討論事項](OPEN_QUESTIONS.md)。
