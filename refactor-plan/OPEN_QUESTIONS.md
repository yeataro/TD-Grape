# 待討論事項

本文件列出已經碰到、但尚未確認的問題。這些不是核准的功能清單，也不是實作順序承諾。答案應從後續討論形成，不從舊草稿或現行程式直接搬入。已確認內容見[重構計畫入口](README.md)。

## 下一題是一般節點的分工

目前停在以下問題：同一種節點的共同規格，與圖內每顆節點本身，要怎麼分工？

曾提出「NodeDefinition 描述共同規格，普通運算共用 Node 實作，特殊行為再使用子類」的方案。使用者尚未回答，不能將這個方案視為已定案。

需要逐步確認：

- 共同規格需要獨立物件嗎？是否採用 NodeDefinition 這個名稱？
- 哪些能力適合用資料描述，哪些需要獨立行為實作？
- 普通運算、來源引用、子圖引用與終端效果，要如何分類？
- Node 子類、定義登記與產碼實作各自負責什麼？

Source 與來源引用 Node 分開的關係已確認；這不代表上列問題也已一併決定。

## 來源列表與實際輸入

- `Source.Uniform`、`sources`、`source.Uniforms` 如何組成一致的型別入口及 Graph 資料入口？大小寫與單複數尚需統一。
- Source 的完整子類清單、各類可用 Stage，以及實例設定如何縮小範圍。
- 常量、特化設定與執行期來源的資料及生效時機如何區分；不能全部套用 Uniform 的預設值模型。
- Source 預設資源如何保存，宿主不支援該資源或轉移失敗時怎麼呈現。
- 刪除或修改被引用的 Source、改變 DataType 時，如何處理圖內引用及宿主既有輸入。
- 已確認宿主管理實際輸入，且排序的效果由宿主綁定決定。宿主物件、回報格式、初始化與重設的詳細流程尚未定稿。

## 接口與 Parameter

- 一個接口可能有多個可編輯屬性，反查 Parameter 的方法應回傳單一物件還是集合？
- 編輯器能用的 type style 與會參與轉換判定的語意提示，使用哪些欄位與名稱區分？
- DataType、接口及 Parameter 各層如何定義允許的 style 與覆寫權限？
- Output 型別或動態接口變動時，既有值與接線如何保留、失效或修復？

## Edge 與轉換

- 接線已佔用、重接、取代及批次接線的精確操作規則。
- 純量／向量的基本元素種類之間，以及矩陣、陣列、結構之間的完整相容表。
- 除 RGB 到 RGBA 補 1 之外，是否加入其他自動擴張規則？
- 共用轉換規則、檢查結果及 Edge 上已選轉換的物件名、方法名與保存格式。
- 型別變動或規則版本更新後，如何驗證及處理既有轉換。
- 轉換提示、漸層接線或輸入標記的實際 UI。

## Stage 與子圖

- Stage 固有規則、節點需求與來源需求的精確合併方式；未宣告與明確不限 Stage 不能混為一談。
- 子圖的有效範圍如何依模式、使用輸出、可達內容及終端效果推導。
- 共用定義修改造成其他使用位置不合法時，哪些動作可保留草稿，哪些需先阻擋？
- 建立獨立子圖時，只複製目前定義，還是遞迴複製巢狀定義？
- 資源庫版本更新、圖內快照在地化與重新連到庫原件的完整政策。
- 跨 Stage 傳值的物件、接口及驗證方式。

## 查詢與編輯歷史

- 全域 Graph 的註冊、生命週期及入口；物件關閉、刪除及復原後的引用行為。
- ID 格式、接孔穩定識別、名稱大小寫、合法字元與重名處理。
- 搜尋條件的精確結構、比對模式及跨子圖使用路徑的結果表示。
- Undo 的內部紀錄方式、歷史容量、工作恢復及是否跨次啟動保存。
- 事件格式、批次修改、失敗時復原，以及對外可直接設定哪些屬性。

## 產碼與宿主整合

這輪已釐清模型與宿主實際輸入的責任，但未逐項確認完整產碼流程。GraphCompiler、CodeGenerator、CompilationResult 等舊稿名稱不可因此視為正式架構。

後續需要討論產碼的入口與結果、診斷及物件位置對照、目標能力差異，以及產碼結果如何交給宿主。接收 GLSL 與來源需求，不等於宿主已成功編譯或套用。

ExecutionTarget、TargetBinding、HostConnection 也是候選名稱。以下議題另外討論，不作為目前 Source 模型的必要前提：

- 同一張 Graph 是否可同時綁定多個宿主實例，以及同步控制權。
- 配對、權限、通訊協定、重連與衝突處理。
- Standalone、TD 及其他目標間的資源移轉與設定保存。
- Electron 與網頁的部署範圍、離線儲存、WebGL 預覽、ISF／FFGL 等交付規劃。
