# 操作與更新

本文整理本輪確認的修改、操作分組、復原、產碼及同步責任。架構提供可調整能力，不在現在固定每種宿主的更新頻率。總覽見[重構計畫入口](README.md)。

## 當前狀態與共用修改入口

Graph 內物件的狀態就是當前圖。Editor 或腳本修改 Node 時已經修改圖，不再抄回另一份正式資料。共用寫入機制檢查本次寫入、更新狀態並回報變更，讓歷史、畫面及更新能力使用。

對外可用屬性 setter 或方法；物件可透過所屬 Network 追溯 Graph。完整的關係驗證與 Error 回報仍依[診斷規則](DIAGNOSTICS.md)處理，不把所有不完整草稿一概禁止保存。

正式修改須能經由這個入口被觀察。是否記錄 History、合併、延後或自動同步可以設定；停用其中一項，不使其他能力失去變更資訊。

## 能力與名稱

| 名稱 | 責任 |
| --- | --- |
| Change | 描述具體修改的資料，例如對象、屬性、前後值、操作與來源；不是另一個管理者 |
| Operation | 一次圖修改操作的歸屬與開始／結束邊界；取代先前 Edit 暫稱 |
| History | 保存足以復原／重做的操作紀錄 |
| Graph.updates | 本圖相關結果的待更新狀態、必要性檢查及執行時機 |
| Binding | 每個接收對象的交付需求、同步策略、請求與完成進度 |
| Editor | 把手勢轉成模型修改，持有選取及導覽，並界定使用者操作的範圍 |

Operation 不是節點的數學運算模式，也不等於一次產碼或一次傳送。Change 的欄位、開始／結束方法及控制物件的最終 API 拼法尚待細化。沒有明確分組的單次修改，也可自動視為一次操作。

## Operation 與 History

每張 Graph 持有自己的 History，包含 Stage、圖內子圖、Node、Edge 與 Source 的修改。同圖的不同 Editor 共用它；Graph 離開 Editor 仍能修改及復原。

操作分組由發起者界定，不靠系統猜每次一定收集幾筆。例如一次批次刪除是整組開始至完成，一次拖曳是按下至放開，腳本也可明確包住一組修改。

一次拖曳十五個節點，單個移動事件可將十五次位置改變合成一批通知；整段拖曳可包含多批通知，History 最後仍記成一次 Undo。滑桿也可即時顯示數值，但將整次拖曳合為一筆歷史。操作邊界、通知批次與交付批次不強制相同。

History 保存需要的前後資料，不要求所有滑鼠中間樣本永久保留。撤銷刪除節點時，必須恢復該節點及受影響的接線。可逆變更搭配必要的局部快照是設計方向；完整算法與容量待定。載入、初始化及外部回報如何排除或追蹤來源，須有明確選項。

Undo／Redo 會改變圖並走共同的變更通知流程；不因此變成一筆普通的新編輯而破壞 redo。History 不需要知道 Generator 或宿主存在。停用或清除復原紀錄，不應停止產碼與同步。

Graph 持有 History 不表示匯出時保存歷史。當前方案先保存當前圖；跨次啟動恢復歷史待定。Grape 層如果要復原新增／刪除整張圖或共用資源，另外討論根層 History，不複製所有 Graph 的歷史成第二份。

## 自訂模組狀態與復原

模組可以定義自訂資料結構，不要求全部轉成固定元件或獨立資源。這份自由仍需搭配可觀察修改與可還原資料的共同契約；登記屬性本身不會捕捉任意巢狀物件修改。

一般屬性可沿用共用修改入口與前後值記錄。自訂狀態由模組提供局部快照及還原能力，是目前討論方向；精確 hooks、差異紀錄與保存格式尚未定案，不要求先實作完整差異引擎。

快照需要保留修改前的實際資料，不能只是指向會繼續變動的同一個物件。若模式變更同時影響接口或接線，復原需涵蓋這些變更，而非只把選單值改回去。檔案序列化與 Undo 可以共用部分表示，但不預設兩者完全相同。

## Updates 歸屬 Graph

每張圖持有 `updates`，記住相關結果可能已受變更影響，以及哪些工作尚未處理。實際產碼使用共用的 `Grape.generator`。多圖執行資源排程與單圖的待更新狀態是不同責任；現在不要求另有 Grape 全域 Updates 管理者。

產碼每次使用當前的一致狀態，不逐筆重播 History。Updates 收到多次變更可合併同一項更新需求，不應因三十次修改就無條件排三十份過期程式等待產生。

提供下列策略的能力，未使用時可立即處理：

- 每批變更立即處理。
- 累積或合併後處理，並可限制頻率。
- 等 Operation 結束後處理。
- 明確手動要求才處理。

每個接收對象可有不同策略。預設值依圖、執行環境及實測成本決定；不現在設定固定延遲或自動調參演算法。產碼與宿主編譯成本分開量測，一幀內完成也需考慮原本畫面與渲染的時間餘裕。

## 只執行必要更新

Change 回報修改事實；Generator／目標及 Binding 依自己的依賴與契約判定哪些結果受影響。不能讓 Node 的 setter 硬編碼每個宿主的特例。

| 情況 | 已確認的預設方向 |
| --- | --- |
| 移動節點或一般節點更名 | 更新圖與畫面，不預設觸發宿主 GLSL 更新 |
| 更名只影響程式碼的可讀名稱或註解 | 可延後到查看、匯出或明確交付最新程式碼時刷新 |
| 改連線、運算設定或圖內常數 | 檢查是否需要重產及交付，再依策略執行 |
| 改 Source／Uniform 實際引用名稱、排序或綁定契約 | 依目標分辨更新綁定、參數定義或程式碼，不一概只改外觀 |
| 宿主即時 Uniform 值回報 | 更新執行期狀態及顯示，不自動改 Source 預設值或重新產碼 |
| 匯出完整圖 | 序列化呼叫當下的當前狀態，不從 History 拼回 |

產碼快但宿主編譯慢時，可以降低交付頻率；產碼本身慢時，在產碼前合併要求。兩者都快可採即時策略。保留能力，不預先假定所有重產昂貴或免費。

## Undo 與結果重用

例如圖內常數由 0.2 改成 0.8，再 Undo 回 0.2：

- 尚未產碼或交付即已恢復時，既有 0.2 結果可能仍有效，可省掉更新。
- 若 0.8 已送出或套用，要確保宿主最後回到 0.2；已有可用的 0.2 結果時，不一定需要重產。

因此有新歷史紀錄不代表必須產碼，不必產碼也不代表不必同步。處理時檢查產碼相關狀態是否真正不同；能便宜判定可提前略過，不能時可產碼後比對結果，減少相同輸出的重送與重編譯。比較、快取及依賴追蹤的做法與成本仍待實測，不能將廉價判定當成已實作保證。

## 排空與完成進度

`flush()` 是目前用來表達「開始處理累積待辦」的名稱，不等於清除所有更新需求。發送成功也不等於宿主成功編譯或套用。

每項工作與每個接收對象獨立記錄處理進度，例如圖目前版本 12、產碼完成到 11、遠端 A 確認到 12、遠端 B 只確認到 9。A 的回覆不能清空 B 的待辦；舊工作完成不能清掉開始後才發生的新修改。版本的表示法與比較協定待定。

產碼結果需對應同一個一致的圖版本。開始後的新變更留待下次處理；是否丟棄、重用或停止過期工作由後續契約定義，但不能讓舊結果覆蓋已套用的新結果。這個要求不等於整套編輯、產碼及網路交付都必須形成一筆可回滾的原子交易。

成功產碼／交付可以記在 log 並引用圖版本，不作為會改圖的 Undo 步驟。History 的操作紀錄與執行結果分開。

## 多人協作保留的能力與未決範圍

多人協作是用來檢查擴充性的情境，尚未選定實作。保留共同修改入口、穩定物件識別，以及變更的操作／來源資訊，使未來能加入權限、鎖、修改接受順序與衝突處理。

Session 暫稱可承擔參與者及編輯權限的責任。鎖需作用於真正被修改的資料，例如共用子圖定義，而不是只鎖其中一個使用實例或停用 UI；斷線後的釋放／到期也需規劃。協調者、鎖粒度、樂觀更新與否、Undo 他人修改的政策都未定案。

單向預覽可依契約只傳最新快照；多人編輯的未確認修改不能直接按同一方式丟棄。可合併或重播的內容由協作協定決定，不能用 Updates 的排程代替衝突解決。多人 Undo 仍是修改，須遵守當時權限與一致性規則；精確演算法留待設計。
