# 接口與接線

本文整理本輪對話已確認的型別、接口、參數、接線及驗證關係。具體方法名和完整規則表尚可細修，未決部分不從舊實作補入。總覽見[重構計畫入口](README.md)。

## DataType 與接口

DataType 描述 Shader 值的型別與結構，包括純量、分量及容器等資訊。它與 Source 的種類、Node 的種類、Parameter 的編輯方式分開辨認。

Input 表示節點接收 Shader 資料的入口；Output 表示節點產生資料的出口。它們持有或提供型別資訊，並可帶有該型別下允許的語意樣式提示。Parameter 是針對資料屬性的可選編輯入口，並不取代 Input 或 Output。

| 物件 | 責任 |
| --- | --- |
| DataType | 值的型別、結構、分量資訊及相容的樣式選項 |
| Input | 接收資料的型別、接線關係、本地輸入值及未接線供值規則 |
| Output | 產出值的型別、用途及下游接線；可調整項目由節點能力限制 |
| Parameter | 編輯指定物件的某個屬性，描述操作範圍、樣式、選項與重設等行為 |

## Input 的本地值

未接線時，Input 可使用圖內保存的本地值；接線後由上游供值，本地值保留，斷線時再使用。`input.localValue` 表達這份本地設定，不表示 GPU 當下算出的結果。

Input 也可以使用固定或上下文供值規則，或要求必須接線。因此「沒有 Parameter」不等於「一定要接線」；是否需要外部供值由 Input 的規則決定。

Input 的初始或重設預設由定義提供權威來源，Parameter 引用該依據，不另存一份會互相矛盾的值。Input 的本地輸入與 [Source 的預設輸入](SOURCES_AND_HOSTS.md)不同：前者參與圖內計算，後者供宿主初始化等流程使用。

## Parameter 是可選的編輯入口

Parameter 綁定它要編輯的對象與屬性，提供編輯規則，不另持有另一份正式資料。它既不是 GLSL 的輸入，也不只是已經畫好的 UI 控制項。

Parameter 可以編輯 Input 的本地值，也可以在節點允許時編輯 Output 的型別或樣式，以及 Source 的相關設定。可選型別與樣式必須受目標能力限制；改變型別後要重新驗證受影響的接線。

NodeType 可明確指定 Input 是否提供 Parameter。提供時，基本編輯規格可從 DataType 與接口樣式取得，再補上特殊範圍、clamp 或樣式設定；不必逐項重寫全部基本規格。接口規格、實際接口及 Parameter 的建立關係見[節點模組與型別](NODE_DEFINITIONS.md)。

以下名稱表達討論方向，尚不是完整簽章：

```ts
parameter.target;    // 被編輯的物件
parameter.property;  // 被編輯的屬性，例如 localValue、type 或 style
parameter.options;   // 如果是選項式編輯，允許的選項
parameter.style;     // Parameter 自己的編輯呈現方式
```

一個接口可以不參數化。當多個屬性都可編輯時，是否對應多個 Parameter，以及從接口反查 Parameter 的單複數形式，尚未定稿；不先固定為一對一。

## 編輯範圍與 Clamp

min、max、default 及 clamp 屬於編輯規則的一部分。Clamp 只限制經過該 Parameter 寫入目標的值，不自動限制接線傳入的資料，也不自動生成 Shader clamp 運算。

例如滑桿可使用 0 到 1 的範圍；若未啟用 clamp，手動輸入是否超出滑桿範圍可以依編輯規則允許。需要限制上游計算結果時，圖必須明確表達該運算。

## 型別樣式與參數樣式

DataType 與接口可提供有限且相容的樣式，例如 RGB、XYZ，或 transform 陣列的提示。這些資訊可供 Parameter 採用，但不要求每個編輯器都實作專用控制項；未特別指定或不支援時，應有最基本的型別編輯方式。

Parameter 可以繼承樣式，或在允許的選項中另行指定。覆寫不能讓編輯值脫離 Input／Output 的實際型別結構。Output 的 style 與「編輯這個 style 的 Parameter」的呈現樣式也要分開辨認。

Parameter 的顯示樣式不改變運算。接口的 RGB 等語意提示可能參與建立接線時的轉換選擇，但不能因後來換了參數控制項的外觀，就悄悄改變已存在接線的計算。style 欄位如何精確區分語意提示與呈現選項，仍需細化。

## 列表與互相查詢

Node 提供自己的 Input、Output、Parameter 列表及單一查找入口。相關物件可以反查所屬節點及編輯目標，關係以單一資料來源維護，反向查詢不另造一份可獨立修改的真相。

```ts
node.inputs;
node.outputs;
node.parameters;
node.input("color");
node.output("out");
node.parameter("outputType");

input.node;
output.node;
parameter.node; // 所屬節點；與 parameter.target 的概念不同
```

畫布與參數面板查詢同一批接口、Parameter 及其屬性，據此建立控制項。介面自行處理排版、字級、主題等呈現，並訂閱模型變更。Parameter 本身不是某一個面板專用的狀態。

## Edge 的責任

底層接線物件明確採用 **Edge**。Wire 與 Link 是同一接線的顯示方式，不作為底層物件名稱。

Edge 連接 Output 與 Input，歸所屬 Network 管理。兩端都是 Node 的接口；Stage 或子圖邊界也透過接口節點表示，端點查詢不新增非 Node 的例外。Stage 透過 Network 的能力管理接線。即使在 Output 上提供 connect 快捷方法，建立、驗證及登記的責任仍需回到 Network。

```ts
const edge = output.connect(input);

edge.from;    // Output
edge.to;      // Input
edge.network;
```

端點應可查詢自己的接線。先前以 `input.connection` 和 `output.connections` 示意；名稱與已佔用 Input 的替換行為仍待細修。

## 依賴循環

普通 Edge 形成的資料依賴不可成環。正常接線檢查 Network 依賴，拒絕造成循環的操作；匯入資料已有循環時保留供修復，回報 Error 並阻止產碼。

子圖定義的直接／間接遞迴也禁止，與同一份定義的多個使用實例不同。明確迴圈能力與 Pass／緩衝回饋不使用普通 Edge 成環來隱含表達。

## 編輯器的自動轉換

自動轉換是圖編輯器的規則，不等同 GLSL 語言的隱式轉換。產碼可以明確寫出 constructor 或分量選取，不把圖的行為交給目標語言猜測。

對基本元素型別相容的純量與向量，已確認的方向如下；這不是完整型別相容表：

| 情況 | 方向 |
| --- | --- |
| 純量到向量 | 可以自動將同一值展開到各分量 |
| 較多分量到較少分量 | 可以自動裁切，例如 vec4 到 vec3 取 xyz |
| 較少分量到較多分量 | 通常需要指定新增分量，不能全部套同一個填值 |
| RGB 到 RGBA | 可以自動補 alpha = 1，作為明確的語意規則 |
| XYZ、UV 等其他擴張 | 討論過補 0、0.5 等可能性，尚未定為完整自動規則 |

基本元素種類之間的轉換，例如 int、float、bool，以及矩陣、陣列與結構等規則尚未在這輪定案。型別推導決定用哪個型別，自動轉換決定已知型別之間如何適配，兩者分開。

## 轉換規則與已選轉換

共用型別規則負責判定允許哪些轉換；Edge 保存這條接線所採用的轉換描述。Input／Output 提供型別與語意資訊，上游 Output 本身不因某條接線轉換而被全域改寫。

轉換描述需要能查詢它的規則來源、實際操作及填入的值。例如選用 RGB 到 RGBA 補 1 後，應留下這個具體選擇，避免之後樣式變動使結果跟著改變。

建立前應可查詢能否接線、原因及預計使用的轉換；建立後也能重新驗證。型別可轉不代表可以繞過 Network、Stage 或其他結構限制。

曾以 ConversionRule、ConnectionCheck、Conversion 三個名稱說明「共用規則、檢查結果、已選轉換」。這組類別名及儲存格式是待細修提案；已確認的是上述責任與查詢能力，不要求先建立這三個 class。

Edge 保持接線與必要適配的角色，不成為隱藏的可程式化節點。需要複雜或使用者持續調整的轉換時，仍以明確的 Convert 等節點表達。

## 轉換提示

提示文字從結構化轉換描述產生，可顯示在接線或輸入端。文字不是運算資料來源，也不靠重新解析提示來產碼。

| 轉換 | 顯示示意 |
| --- | --- |
| vec4 到 vec3 | `Output1.xyz` |
| vec4 到 vec2 | `Output1.xy` |
| RGB 到 RGBA | `vec4(Output1.rgb, 1.0)` |
| 純量到 vec3 | `vec3(Output1)` |

Output1 是可讀的來源名稱，不一定是實際 GLSL 符號。更名可以更新提示，不改變轉換。這也不會憑空建立一個名為 xyz 的新 Output。接線漸層、輸入標記等顯示位置尚未固定。

## Stage 相容性與驗證

Stage 的固有能力與基本限制，搭配節點註冊的可用 Stage／能力需求，共同決定能否使用。來源種類也有自己的可引用範圍。選單分類、家族顏色不直接充當驗證規則。

子圖的相容性由內容與巢狀引用導出，並在實際使用的 Stage 上下文中檢查。共享定義被修改時，要考慮其他使用位置，不能只驗證目前正在編輯的那一處。

驗證包含拖入前、編輯後、載入及產碼前等時點，使用共通規則。手動修改資料造成不合法內容時，保留可修復的資料並提供診斷；不能靜默刪除內容或自動將共用定義拆成副本來掩蓋問題。

Error 阻止受影響圖與產碼目標的產碼，Warning 不阻止。錯誤狀態仍可保存及重新載入修復。不同作用域的診斷要保留歸屬，不把別張圖的錯誤當成全域阻擋；也不另設「不在輸出鏈就忽略這張圖已有 Error」的例外。詳細門檻見[驗證與診斷](DIAGNOSTICS.md)。

依賴追溯不能只從有輸出接孔的節點開始。本輪沿用的終端行為包括 Discard、TDAlphaTest、Depth Output 這類無輸出也有作用的節點；被使用的子圖可帶入終端效果，未使用的定義不自行生效。

Stage 大類規則與節點註冊的精確合併方式、未宣告能力的意義、子圖逐輸出或逐模式的相容性，以及診斷資料結構仍待細化。尚未完成的圖可以保留為可編輯草稿；各種編輯動作何時阻擋、何時允許保留錯誤，不能在本文件中一概決定。

## Network 的放置範圍

可用 Stage 與可放置的 Network 角色是兩個需要一起檢查的條件。某個節點能在 Pixel 執行，不表示它能放進 Pixel 使用的子圖。

| 節點角色 | 放置範圍 |
| --- | --- |
| Source 類引用節點 | 符合來源與 NodeType 限制的 Stage 根 Network |
| Stage Input／Output 節點 | 對應 Stage 的根 Network |
| 子圖自身的接口節點 | 對應子圖的內部 Network |
| 其他節點 | 依其 Stage、Network 角色及能力規則驗證 |

Source 類與 Stage Input／Output 節點不能置入子圖。子圖使用自己的接口接收外部資料，不在內部另外放來源引用或 Stage 端點。這項規則不依賴它們是否被放在同一個新增選單分類。

共用放置驗證涵蓋新增、貼上、匯入與後續編輯／產碼；只過濾新增選單不足以保證規則。放置需求的註冊欄位與各情境的回報 API 尚未定稿。

## Stage 接口仍透過 Node 接線

Stage 接口定義與其在 Network 裡的節點投影分開。實際 Input／Output 仍由 Node 持有並遵守共用身分、型別與 Edge 規則；必要端點節點的不可刪除限制也由模型執行。

跨 Stage 傳值有獨立於 Source 的共用定義，Stage 兩端引用它，Edge 不跨 Network。正式命名、傳遞設定及系統接口與使用者接口的增減規則見[圖與編輯器](OBJECT_MODEL.md)，精確契約仍待細化。

## DataType 的登記與作用域

Grape 持有共用 DataType，Graph 可持有本地結構或型別，更下層在需要時也可有自己的型別作用域。查詢先找目前作用域，再往父級查詢；不把所有父級定義複製成子級可各自修改的副本。

模組提供的型別與圖內自訂結構都須能經這些入口查詢。節點宣告結構時，必須明確指定歸屬與引用，使編輯器可判斷接孔型別，產碼器可收集宣告與依賴。

DataType 的穩定身分與可讀名稱分開。不同作用域可有同名定義；名稱查找可優先得到較近的定義，但已綁定接口不因新增同名型別而偷偷改指向。相同作用域的衝突須明確處理，不用載入先後覆蓋。

產碼依型別身分管理宣告與依賴，避免重複宣告並配置不衝突的 GLSL 符號。同名不自動等於同型別，相同欄位結構是否可視為等價仍待決定。型別作用域與 API 的精確層級尚可細化。

## Source 樣式與宿主控制項

Source 也能提供型別允許的 style，供圖內及宿主自訂參數呈現使用。bool 可用 toggle、選單或受控數字輸入；向量可用分量或顏色控制；整數列表保存實際整數值及獨立顯示標籤。

style 本身不改變 GLSL DataType。控制項到值的映射可以由共用編輯能力或宿主適配提供，不等於新增 GLSL 轉型節點。允許的映射範圍須受型別與來源能力限制，不因討論過某個極端例子就自動開放任意型別映射。

pulse／event 等按鈕行為由執行宿主管理；若由 Grape 提供 WebGL 執行環境，它也需要實作對應行為。各宿主能呈現哪些 style、遇到不支援時如何回退，另列規格。
