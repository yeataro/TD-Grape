# Uniform 可編輯狀態與圖更新的分工

2026-09-20，依 0.8.153 後使用者 review 整理。這輪只調查、分類與提出修正原則，尚未修改產品保護邏輯。

## 核心判斷

圖有差異本身，不構成停用 Uniform 數值的理由。圖需要保存、重新產碼或編譯，與某個 Uniform 的原生 Parameter 是否仍可寫入，必須分開判斷。

0.8.153 已排除位置／尺寸等外觀變更，但其餘修改仍沿用整份圖內容差異作為保護依據；這是保守的實作限制，不能當成產品必須如此的規則。是否位於 Color Output 上游流程，可協助判斷運算內容是否受影響，卻也不能直接決定是否停用 Uniform。

## 建議實作方案（先報告，尚未實作）

### 以來源的可寫狀態決定數值控制

讓 Uniform 數值控制取得自己的來源與分量狀態。已有 TD 原生來源、目前仍指向同一 Shader／Parameter、型別與對應仍相符、最終目標可寫，就可操作。圖的 dirty、待保存或編譯中，不再單獨成為整批 Uniform 停用的理由。沿用現有來源 ID、快照與原生身分核對，不建立另一份使用者來源清單。

本地草稿若改變某個 Uniform 的來源定義，先暫停該來源；不能只因伺服器仍存在舊 Parameter 就繼續把新定義的值送到舊目標。其他未受影響來源保持可用。真正切換 Shader、整體狀態不明或唯讀時，才適用整體限制。不可寫的 Expression／Export／Binding master 仍由分量本身決定。

### 保存／編譯與調值交錯

- 即時通道繼續固定原生 Parameter 身分；Apply 前後目標有效時維持手勢，目標失效時停止受影響手勢並重新取得來源。
- 使用 REST 的值寫入沿用序列化：等待已在途的 Apply，再核對載入世代、目標、預期值與目前版本；不送出舊版本請求，也不把舊預期值默默改成新值以掩蓋衝突。等待期間以送出狀態處理，避免整批呈現不可編輯。
- Apply 回覆需要有可靠的來源相容性依據：檢查目前來源配置／原生身分核對是否足以提供確認，再決定是否補最小的回覆資訊。不能只憑 `shaderUpdated=false`、產碼相同或前端宣告相同，就猜測原生目標沒變。
- 保留來源值與歷史的權威性：舊輪詢不得倒退版本，圖保存回覆不得用舊值覆蓋正在調整的讀數；Undo／Redo 維持操作順序與各自的值／圖變更範圍。

### 第一批範圍與驗收

先解開 Uniform 值的可用性與整份圖差異的耦合，配合必要的 Apply 回覆／原生核對。是否跳過流程外編輯的重新編譯是另一個效能判斷，不把它當成本批保持 Uniform 可操作的前提；不改圖文件格式、不因這項修正更動現有產碼語義。

正向驗收包含本輪回報：流程內外改分量名稱、自訂名稱、常數值、流程外 Combine 型別與節點刪除；在保存回覆延遲時仍能開始／持續／完成有效 Uniform 調值。另核對「重新產碼但 Uniform 未變」的情況。

反向驗收包含真正刪除／改型別／改名 Uniform 來源、原生參數被替換、Binding 轉向或變成不可寫、外部改值、切換 Shader、失聯及真正版本衝突。確認必要的拒絕仍存在，且不影響無關來源；再驗證 Apply 成功／失敗／回滾及 Undo／Redo 交錯，不漏值、不寫錯來源、不讓舊回覆覆蓋新狀態。

目前是待討論方案。Uniform 滑桿移除把手／恢復一般高度，以及 Note 外觀回饋另行追蹤，不混入這份保護規則方案。

## 目前為何會觸發

- `src/editor/app.js` 的 `graphContent()` 排除座標、尺寸、部分展開狀態及 Note，卻仍保留其餘所有節點、參數、`ui.label`、`ui.componentNames`；不先依 Color Output 上游流程裁切。`hasShaderChanges()` 比較這份資料與已保存內容。
- `src/editor/inspector.js` 的 `sourceReady()` 受到未同步圖、Apply 中、來源快照版本不一致、來源錯誤、唯讀及操作鎖限制。`uniformValueReady()` 只額外放行上述比較認定為外觀修改的情況。因此流程外刪除、型別修改、分量名稱及一般內容編輯仍會停用數值。
- 保存成功後，0.8.153 只有在原先判定為 layout、TD 確認未重建 Shader、原快照版本與內容吻合時，才直接推進來源快照版本。其他操作仍可能等待來源刷新，形成灰掉後恢復的間隙。
- 後端 `src/core/sgrape_core.py` 的 `clean_semantic()` 雖排除 UI，仍把未參與輸出的節點放入圖雜湊。`src/td/runtime/sgrape_runtime.py` 的 `_deploy()` 要求圖雜湊及現有產碼都相符，才走只保存的路徑。因此某些流程外編輯，即使產出 GLSL 完全相同，也會走配置／驗證路徑。

畫面的灰色可能來自上述整體可編輯條件，也可能來自原生分量本身不可寫；兩者不能混為同一個理由。

## 本輪回報的判別

| 操作 | 已知影響 | 對 Uniform 的合理處理 |
| --- | --- | --- |
| 移動／調整尺寸 | 外觀資料 | 保持可用；0.8.153 已修正，使用者確認移動正常。 |
| 刪除 Color Output 上游流程外的一般節點 | 圖文件改變，未必改變有效產碼 | 不應僅因此停用。刪除畫布引用與刪除原生來源須分清楚。 |
| 流程外 Combine 改型別 | 流程外節點內容 | 不應僅因此停用無關 Uniform。 |
| 流程內／外改分量名稱 | 既有規則只改顯示標籤，不改 port ID 或數值順序 | 不應因此停用。 |
| 節點自訂名稱 | `n.name` 會參與 GLSL 局部變數命名；與 `ui.label` 產生註解、Uniform 原生來源改名是不同欄位 | 不應僅因局部變數改名停用 Uniform。 |
| 修改參與輸出的常數數值 | 通常更新 GLSL／編譯結果 | 不自動停用其他 Uniform；核對原生寫入目標與配置交易即可。 |
| 其他流程內設定 | 需看具體欄位及依賴 | 按來源影響判斷，不能以「在運算流程內」一律停用。 |

使用者尚未逐一確認每個設定。上表是依已讀程式與下方比較提出的處理原則，不等同所有操作已完成原生驗證。

## 真正要保護的情況

1. **寫入目標改變或失效**：切換 Shader、Uniform 來源被刪除／替換／改型別、原生參數列改名或搬動、Binding 目標改變。重新確認目標前停止舊手勢，範圍優先限於受影響的來源。
2. **目標本來就不可寫**：Expression、Export、不可編輯的 Binding master、唯讀或已停用的原生參數。這是該分量的可寫性，不是圖文件的 dirty 狀態。
3. **寫入結果或目前狀態無法確認**：失聯、過期回覆、實際版本衝突、來源快照不可靠。需要重新核對，不能盲目重送到未知目標；單純版號因保存而增加，不等同寫入目標失效。
4. **真正修改來源配置的交易期間**：必要時暫停受影響寫入，或序列化後核對再送出。恢復依據是原生目標已確認，不是所有圖保存工作都已結束。

後端已有可保留的保護：`src/td/runtime/sgrape_live.py` 的 `Source.check()` 固定來源及 Par 身分，`Gesture.validate()` 檢查模式、Binding 目標、外部改值與限制；`graph_changed()` 針對來源 type/name/kind/sourceMissing 失效。`src/core/sgrape_sources.py` 的 REST 寫入會核對版本、預期值、原生對應及最終可編輯目標。

後續方向是讓前端可用性與這些實際條件對齊，保留後端核對，將保存排程、編譯狀態與原生值操作拆開。需要排隊或核對的寫入，不必一律表現成全部 Uniform 灰掉。Undo 的歷史順序、Apply 回覆與來源更新交錯仍須測試；不能直接刪除所有 busy／revision 判斷。
