# 來源建構、型別與 MAT Attribute：討論共識

2026-09-20。接續[來源選單分類表](TD_SOURCE_MENU_REVIEW.md)與[來源命名總表](TD_SOURCE_NAMING_RESEARCH.md)。本頁記錄設計方向與待決項，不代表已完成來源重構或新增能力；產品基線仍為 0.8.120，交付狀態以 [STATUS](../development/STATUS.md) 為準。

本輪回到的主線是來源資料模型、共用建構方法，以及 MAT Attribute。延伸的 Loop／控制流程先收進[迴圈筆記](LOOPS_DISCUSSION.md)，不因此插入本輪實作。

## 1. 用資料擴充，行為由共用方法實作

- 節點表登記可加入的項目；來源實體及其引用可以另有來源表。是否合併實體檔案尚未定案。
- UI 分類／名稱與建構行為是兩種屬性。改分類不應要求改建構器、型別檢查或 GLSL emitter。
- 同類固定行為共用方法：直接建立圖節點、建立 Uniform、引用內建來源、配置 Texture Input 等；項目提供型別、名稱、初始化資料及適用範圍。
- 表格選擇明確的處理方法與參數，不先建立任意流程腳本語言。分類不向 TD 查詢，不為每一候選複製整張圖模擬接線。
- 宿主／圖種類與 Stage 分開描述有效組合，例如 TOP Pixel、MAT Vertex／Pixel；未來 POP 是圖種類，Compute 是 Stage。未支援組合不能因分類資料出現而變成可用。

目前節點庫已有 browser metadata，但 Inputs 預置、來源分組、部分可用性與建構分派仍分散於前後端；此次共識不是現況已全部資料化的宣稱。

## 2. 建立、引用、修改各有責任

| 操作 | 設計共識 |
| --- | --- |
| 建立來源 | 預置只描述首次初始化，例如型別、Value／Expression 模式與初始 expression；已有同名實體時拒絕重複建立並回報已存在，不默默改成修改或新增另一份。 |
| 建立引用 | 指向已存在的來源；不重做來源初始化、不覆蓋使用者修改過的 TD 值或模式。 |
| 修改來源 | 明確修改指定實體；型別、名稱、綁定等依各自規則處理，不借用重複建立來隱式修改。 |

預置 UI 的構想：尚未初始化時顯示有分類色的項目及新增入口，建立後變成可引用來源。後端仍查驗實際宿主實體，不只相信 UI 狀態。名稱可作為查找依據，但既有穩定來源身分與重新命名關係須保留；具體資料格式尚未定案。

TD-specific Expression、原生 Parameter 位置與相對求值環境由 TD 處理方法負責；不能因來源表共用就假裝它們與宿主無關。來源初始化不在 Open Editor、重新引用或 Apply 時反覆執行。

Uniform 的即時值／模式仍由 TD Parameter 持有；圖保存引用與必要配置，不複製高頻值進圖保存。Spec Constant 可以共用身分／型別／原生列配置等基礎方法，但特化 ID、支援型別與生效方式需保留；具體共用範圍尚待整理。

Texture 的程式入口可共用，再分派 TOP／MAT 各自方法。TOP 的 slot、實際輸入與連接管理，和 MAT 的具名 sampler 配置不是同一份實作；不為共用入口強迫它們完全一致。

## 3. 結構定義、接口與型別傳遞

- TD 內建、節點庫提供、圖內自訂的結構都能向共用型別機制提供定義。圖與節點庫在「提供定義」的能力上可共用格式，整體職責不等同；同名資料不能默默互相覆蓋。
- 接線比對穩定型別身分，不只比顯示名稱，也不因兩份結構欄位碰巧相同就當成同一型別。
- 型別的來源與宣告責任分開：TD 已宣告的結構登記後引用；圖擁有的結構需要時由產碼器宣告。共用型別檢查不抹除這個差別。
- 同一節點可同時提供「完整結構」與「一般欄位」出口。哪些欄位直接露出由接口設定決定，不強制所有來源都拆成另一顆 Field，也不要求所有欄位全部露出。
- 結構表提供欄位名稱／型別；節點定義選擇來源及出口；共用 emitter 產生 `value.field`。多出口引用同一函式結果時應共用結果，不因每個欄位重算函式。
- 自訂結構接入同型別入口；Array Create 的泛型規則接收合法、受支援的元素型別並建立 `T[N]`。並非自訂結構逐一列出能接哪些節點，也不是所有資源型別都能當一般陣列建構／填值。
- `Array[i]` 從陣列型別取得元素型別，例如 `Particle[N] -> Particle`；不用讀取元素值或先算出 N。要拆欄位時才查結構定義。
- 新增結構定義不自動賦予 Add 等運算語意，也不生成全部型別兩兩相容的巨大配對表；沿用同型別、陣列元素及欄位等共用規則。

這些是擴充方向。已有能力與限制見[陣列與結構](../features/ARRAYS_AND_STRUCTURES.md)；自訂結構作者 UI、所有內建來源的完整／欄位雙出口尚未因此完成。

## 4. 編輯器、產碼與錯誤邊界

圖可以視為結構化程式編輯器；可借鑑 IDE 的型別／名稱解析與診斷共用方式。「提示或阻擋」是編輯政策，與是否有產碼／編譯能力分開。

- 可直接判斷的接線／圖錯誤提前攔截；不為得到所有答案去模擬 GLSL 執行、求值常數鏈或持續同步宿主狀態。
- 圖到 GLSL 是一種程式表示轉換；完整 GLSL 編譯由宿主編譯鏈負責。編輯器不知道具體長度，不等於來源不能表達。
- 明確不合法的編輯可以拒絕；編輯草稿、成功產碼、最後成功的 Shader 是不同狀態。「回退」需要說明回退哪一層，不一律撤銷使用者內容。
- 未來自訂節點／程式碼以宣告接口供圖檢查；使用者負責自訂內容，我們仍負責包裝、產碼與編譯失敗處理。既有 GLSL Code 能力不因這份後續方向被說成不存在。
- 編譯診斷應追溯到節點與自訂碼行號，節點紅色圓圈叉號為使用者提出的呈現方向；保留內容供修正，執行端保留最後成功結果。具體 UI／映射覆蓋率未驗收。
- 編譯器指出的位置不保證是根本原因；不可把我們的產碼錯誤一律歸責使用者。沒有承諾零錯誤或以「千萬分之一」作為已量測機率。

## 5. MAT Attribute：回到來源主線的待辦

使用者要求列入來源整理：Attribute 配置主要是在描述要引用的幾何屬性名稱，而非由圖持有每個頂點的值；需要處理常用預置、使用者自訂名稱，以及對應型別／陣列大小。實際值仍來自宿主幾何資料。

### 初始來源仍待決

- 使用者傾向讓常用 Attribute 一開始可用，但「有哪些預置」「是清單已有可引用項目，還是建立 TD 配置列」尚未定案。
- 「定義了而未使用也沒差」先保留為使用者預期，不當成已驗證所有宿主配置都零成本、無名稱衝突或無相容性影響。
- 後續區分宿主本來就提供的 accessor，與需要使用者指定名稱／型別的 Attribute；不因顯示預置而重複建立原生資源。

### 官方介面核對

2026-09-20 核對官方文件，未操作 TD、未做新 Attribute 實機驗證：

| 官方項目 | 核對結果 |
| --- | --- |
| GLSL MAT Attributes 頁 | `attr` sequence 包含 Name、Type、Array Size；目前文件列 scalar／vector 的 float、double、int、uint 系列，size = 1 表示非陣列。 |
| 幾何 Attribute 存取 | MAT Vertex 可用 `TDAttrib_<name>(arrayIndex, vertexIndex)` 與陣列大小資訊；陣列大小指一個 Attribute 內的元素數，不是幾何頂點總數。 |
| 常用內建 accessor | `TDPos()`、`TDNormal()`、`TDTexCoord(layer)` 由宿主提供，不需要再次手寫宣告。 |

Matrix（矩陣）與 Attribute 的來源歸屬、各自配置及 Array Size 的適用對象，接續依宿主介面整理。

## 6. Buffer 來源缺口

來源總表已列出 Buffer 家族，但此前執行清單未單獨列入，目前也未實作完整的配置／引用／讀取流程。需要區分兩種已列來源：TD Buffers 頁配置的 POP attribute buffer（POP 路徑、Point／Vertex／Primitive class、Attribute 名與 Shader 名），以及 Arrays 頁由 CHOP 提供的 Texture Buffer（samplerBuffer／texelFetch）。它們均不可因資料像陣列就當成既有 Uniform Array；原生 Uniform Array 匯入目前會診斷並拒絕 Texture Buffer 模式。

卡片外觀、選取、Help 與右鍵操作可共用來源 UI；來源配置、可用型別、讀取／長度及錯誤處理需各自適配。補齊目前 TOP／MAT 的來源能力不等於實作整個 GLSL POP 宿主，也不包含任意可寫 SSBO。Buffer 的型別／讀取策略仍需實機確認，不能標為已完成。

官方依據：[GLSL TOP 的 Buffers 與 Arrays 參數頁](https://derivative.ca/UserGuide/GLSL_TOP)。研究表既有列 S150、S158–S160。

2026-09-20 使用 `tests/td/probe_buffer_sources.py` 在 TD 2025.32820 的隔離元件實測：未接線的 In CHOP 為 0 channels、1 sample，自身無錯誤；空的 In POP 自身亦無錯誤，但將其 P 綁定至 GLSL TOP Buffer 後會報 Attribute not found，讀取函式編譯失敗。有效 Line POP 的 P 可以成功編譯；指定不存在的 Attribute 亦會報錯。空 In CHOP 綁定為 Texture Buffer 時，此版 TD 允許 samplerBuffer／texelFetch 編譯，但測試未驗證取值內容，不能推論一定補零或可安全讀取空 buffer。測試元件已清除，未更動使用者圖。私人報告：`work/reports/source-buffers/native-empty-probe/result.json`。

輸入缺失需分辨「入口存在」「資料／Attribute 可用」與「Shader 可以讀取」；UI 可保留來源配置並提示未就緒，不自行把缺失內容當成零值。外部輸入在已套用後被拔除時，保留最後成功的 Shader 程式碼不等於保證 TD 仍能產生最後成功畫面。缺失輸入的產品行為與 recovery 仍需和來源功能一併驗證。

## 接續順序

### 本輪執行範圍

使用者授權以能力優先，內容能沿用同一機制完成則一併補齊；Common Uniform、一般 Uniform 與未實作的 MAT Attribute 為重點。Attribute 的資料模型與 UI 由開發端整理，完成後提供具體流程與驗證供使用者審查。此授權不等於要求把研究表中的運算、未支援宿主／Stage 或所有候選項目一次上架。

結構作者介面採獨立面板、預設左側，面板列出結構並提供新增／編輯入口；新增與編輯使用彈出式面板，包含名稱、欄位名稱、共用型別選單及新增／刪除。結構建立後登錄圖內定義，其他結構以型別引用，不另做二級／三級結構的專用操作。編輯前呈現受影響的引用，修改接口後推導相關接線，包含 Array[i]、Field 等型別傳遞鏈；保留穩定 ID 與仍相容連線，不相容／不存在接口沿用既有斷線與診斷規則。具體處理由開發端依現況整理，交付時說明。

UI 更新需區分定義變動與資料讀取：新增型別不重建未受影響的圖節點／來源清單；選單按需取得最新定義，使用中的型別修改只使必要接口／診斷失效。實際策略以既有更新流程與量測為準，不為此先重做整套狀態管理。

面板中的結構與來源使用共用的可收合卡片外觀（標題列／Body），選取後在 Help 顯示完整內容；編輯、刪除等動作集中於右鍵選單，觸控亦需可開啟同一選單。結構新增／編輯對話框提供備註欄位，備註與完整欄位定義可在 Help 閱讀。純備註修改不觸發接口與接線檢查；欄位／型別修改才檢查受影響的型別使用處及傳遞鏈。

Uniform 來源本體與圖上的來源引用是兩個操作對象：兩者可開啟同一來源的編輯入口，但刪除引用只移除節點，刪除本體才處理其他引用的影響。結構則是型別定義，不套用 Uniform 的建立來源／引用來源流程；結構修改後要處理的是使用該型別的節點、欄位與接線。共用卡片元件不代表共用不適用的生命週期或右鍵動作。

結構也會被引用：這裡指使用同一份型別定義，而非 Uniform 的來源實體／引用節點之分。從面板或相關圖節點進入編輯時，共用同一套編輯介面並以穩定 ID 定位同一份定義／來源，不另存一份引用端可獨立漂移的內容。Uniform 實際值仍由 TD 參數持有；結構欄位由圖內型別表持有。位置、自訂顯示名稱等節點個別屬性仍屬該節點。共用定義的修改需提示受影響的使用處，避免把全域修改誤認為僅修改單一引用。

UI 不必要求使用者區分「本體／引用」：面板卡片與圖上的相關節點可以直接呈現同一個來源或型別，從任一入口編輯共同內容。實作仍以穩定 ID 維持單一內容與各使用處的關係。刪除動作用語需明確區分「移除節點」與「刪除來源／結構」，避免移除一處畫布呈現時意外刪除共用內容。

TD vector Uniform 的 UI 依宣告型別顯示有效分量（float 一格、vec2 兩格、vec3 三格、vec4 四格），不因原生列提供四格就全部畫出。面板卡片及圖內 Uniform 節點可使用共用的分量數值輸入／滑桿，直接編輯同一原生來源；維持拖動即時傳值與 TD 回傳同步，更新數值不觸發圖存檔、產碼或無關 UI 重建。隱藏未使用分量不代表清除或重設 TD 中的值；Expression／Export／Bind 等原生驅動狀態仍沿用既有編輯權限。

畫布分量各自依原生模式呈現：Constant 與 Bind 可編輯數值／滑桿，Bind 寫入不得切換或解除綁定；Python Expression 與 CHOP Export 不呈現分量編輯滑桿，原位置直接標示 Expression／CHOP Export，說明可提供 expression 或來源通道。此輪先以模式提示為主，是否額外顯示即時結果留待使用回饋；不要把整個 Uniform 因其中一格被驅動而全數鎖定，也不要只靠顏色表達狀態。

節點內與 Parameter 面板均沿用一般有分量節點的共用編輯元件，依宣告型別顯示分量數，排列與操作一致。Uniform 在該元件上接入原生來源同步與逐分量模式辨識／可編輯性，不另造一套 Uniform 專用數值控制。

執行分批與完成檢查點：

- [ ] 共用來源資料表、預置初始化與分類資料，保留既有來源識別／原生值所有權。
- [ ] Common Uniform 與一般 Uniform 的建立／引用流程、缺少的基本時間預置。
- [ ] MAT Attribute 的原生配置、引用／修改、圖產碼、失敗保護及 UI。
- [ ] Buffer 來源的配置／引用、讀取與長度能力：POP attribute buffer 與 CHOP Texture Buffer 分別確認及驗證。
- [ ] 結構定義面板、巢狀型別引用、完整結構／欄位接口與局部 UI 更新。
- [ ] 可沿用機制的來源內容補齊，TOP／MAT 回歸、TD 同步、逐批 Git／TOE 檢查點與交付說明。

以下是整理順序；Loop 控制流程仍留待後續。

1. 繼續來源表／節點表、共用建構方法與生命週期的方案整理。
2. 把 MAT Attribute 的型別、名稱、array size、內建 accessor 與預置初始化納入同一來源模型；整理 Matrix／Attribute 的歸屬與預設清單。
3. 依既有功能整理可實作範圍與驗收，再進入產品修改。Loop、一般控制流程擴充及新的自訂節點作者介面先留在後續筆記。
