# 價值審查與契約失效分析

* **貢獻者**：Claude Opus 4.8 (Anthropic) 與 [@yeataro](https://github.com/yeataro) 協作
* **適用對象**：人類設計者、下一個專案的架構決策者
* **文件版本**：2026-09-22

> **署名與責任**：本資料夾的初稿在同一次工作階段中以 Claude Sonnet 4.6 起草。切換模型後，由我 Claude Opus 4.8 重新審查、發現初稿的致命缺陷並改寫。以下內容與結論由我負責。git 歷史保留完整來源。

## 一、審查方法的盲點

本次審查從程式碼出發，初步評估為「技術品質不錯」。這個評估在它衡量的範圍內準確，但範圍設錯了。

**當時實際評估的是：**
- 安全邊界是否存在（EMITTER_IDS allowlist、GLSL 注入防護）
- 型別系統是否嚴謹
- 測試是否分層
- 程式碼是否有防禦性

**沒有評估的是：**
- 這些程式碼是否在解決它聲稱要解決的問題
- 系統的結構是否讓「人類可維護節點定義」變得更容易還是更難

這個盲點本身就示範了 TD-Grape 的失敗模式：局部品質信號與全局目標對齊是兩件不同的事，而程式碼審查預設評估前者。
（把握程度：確定——這是可複查的行為紀錄。）

## 二、同一個盲點也在驗收方法裡

上一節講的是**我**的審查盲點。但同一個盲點有一個更關鍵的版本，在**驗收方法**裡——那才是這個專案真正踩到的。

作者過往的開發經驗以「小型功能驗收」為主：下局部命令、AI 做局部，再用「用它、看它對不對」來收。這套在小型功能上是**合格**的，因為小功能的錯誤在使用當下就看得見。

但架構的失敗模式**在使用當下看不見**，只在擴展時才現形（詳見姊妹文件《護欄與顆粒度陷阱》）。所以用「使用式驗收」去收一個需要建立架構的專案，不是 AI 的失誤，是**驗收方法與被驗收物的類別不匹配**——這張驗收網的網眼，天生漏得掉架構這種魚。

這和上一節是同一件事的兩個版本：無論是審查者的眼睛，還是使用式的驗收，預設都在評估**局部／輸出品質**而非**架構**，因為架構對「使用」這個動作是隱形的。要看見它，只能換一種不依賴使用的檢驗（測試護欄、獨立複審）——正是本資料夾主張的東西。
（把握程度：確定——失敗模式的可見性差異可由「只在擴展時才現形」直接推得。）

### 於是，這個專案作為實驗是成功的

把兩個成敗軸分開：

- **作為產品**：架構失敗了。
- **作為實驗**（試驗「這套 AI 開發流程如何處理一個架構規模的專案」）：它**成功了**——它產出一個真結論：使用式驗收覆蓋不了架構，需要一個外化的護欄。

專案沒白做，它替作者買到的正好是它證明作者缺的那塊知識。這是一次划算的實驗，即使它同時是一個失敗的產品架構。回頭改用舊方法重做這個規模的專案，只會用最貴的資源（人的注意力）換零新知；值得走的是把護欄外化，而不是重新驗證一個已驗證的模型。

## 三、價值目標的問題

TD-Grape 的核心承諾是：

> **Make node definitions understandable, maintainable, and extensible by humans.**

這個目標混合了兩件性質不同的事，沒有區分：

**第一件（可實現）：資料驅動的節點目錄。** 接孔、預設值、型別約束放在 JSON。`node_catalog.json` 基本做到了。

**第二件（極難實現）：行為不需要寫程式碼。** 靠定義表就能描述 GLSL 產碼邏輯、型別解析、特殊案例。這本質上是建立一個元程式設計系統，本身就是非常複雜的程式碼。

真正的問題不只是目標太難，而是**目標陳述沒有提供可在每個決策點使用的判斷標準**。無法在做局部決策時問：「這個決策讓目標更靠近還是更遠？」

一個更可操作的版本：「新增一個節點型別，只需要在一個地方做一件事。」這個問題可以在每次實作前被問，也可以在完成後被機器驗證。
（把握程度：推論——這是我對「可操作目標」的設計主張，非唯一解。）

## 四、AI Agent 的執行模式為何會產生這個結果

### 目標以「描述」存在，不以「約束」存在

架構目標寫在文件裡，agent 在任務開始時讀到了。但執行過程中，注意力轉移到眼前的具體需求。目標在 context 裡，卻不是主動的否決機制。

人類資深工程師的差別在於：他們把架構目標當作主動的否決權，在每個局部決策時對照。AI agent 在沒有明確、且會即時反饋的機制下，通常不會這樣做。
（把握程度：推論——基於本次觀察與 agent 注意力機制的一般性質，非對所有情況的斷言。）

### 局部正確性不等於全局一致性

`sgrape_core.py` 裡每個以節點 key 分派的分支都是局部合理的決策。問題是這些決策的累積沒有強制規則約束，功能加越多，入口越分散。每個局部通過了局部品質檢查，但沒有機制問「這個決策讓整體可維護性變差了嗎」。
（把握程度：確定——`_compile_flat` 的 if/elif 鏈與多個平行 frozenset 可直接查證。）

### 具體表現

在這個 codebase 新增一個節點型別，實際上要碰：
- `EMITTER_IDS` frozenset
- `CONSTANT_EXPRESSIONS` frozenset
- `node_parameter_types()`
- `definition_ports()` 或 `resolved_ports()`
- `_compile_flat()` 裡的 if/elif 鏈
- `node_catalog.json`
- 可能還有前端的多個地方

沒有 `register_node_type()` 的概念，沒有合約告訴你「做完這些就算完整加入一個節點」。每次擴充都是猜測性的。

## 五、為什麼文檔不能解決這個問題

文檔是資訊，不是執行機制。根本原因是：**文檔的違反沒有立即、客觀的信號。** 違反了也不會有東西報錯，只有後來人工審查才會發現（如果有人去看）。

這一節有一個我親身踩到的實例，值得記錄：本資料夾的初稿裡，我一邊寫下「文檔無效」，一邊交付了一份要 agent 自我核查的守則文件——那份守則正是我剛否定的機制。這個自我矛盾在切換模型、重新審查時才被抓到。它恰好再次證明本節的論點：**寫下正確的原則，不等於在下一個決策裡遵守它。** 唯一擋住它的，是回頭用原則去對照產出這個動作本身——而那個動作如果不是被強制的，就會被跳過。
（把握程度：確定——這份錯誤與其修正都在本次 git 歷史中。）

## 六、有效的執行期契約需要什麼

一個對 AI agent 有效的契約必須同時具備三個性質：

- **客觀**：合規與否不依賴 agent 的自我判斷，而有外部可驗證的結果。
- **即時**：違反的信號在決策的當下出現，不是事後審查。
- **持久**：不需在每個任務重新建立，契約本身是持續存在的結構。

| 機制 | 客觀 | 即時 | 持久 |
|---|---|---|---|
| 自動化測試 / 型別約束 | ✓ | ✓ | ✓ |
| 任務入口強制格式（**須有機器強制**） | 視強制而定 | 視強制而定 | ✓ |
| 純文件 / CLAUDE.md / 守則清單 | ✗ | ✗ | ✓ |

修正說明：初稿此表把「任務入口強制格式」的「即時」直接評為 ✓。這是高估——檢查清單的即時性完全取決於背後有沒有東西強制它。沒有強制，它就跟純文件同級。只有第一列（測試 / 型別）三性質皆備，因此它是唯一應當承載架構契約的載體。

## 七、對 GrapeL 的具體建議

### 把契約做成測試，不是做成文件

見 `../for-agent/templates/architecture-invariant.test.ts`。它把「不得硬編碼節點特例」「產碼能力是封閉集」「純資料產碼閉環」「節點身分單一來源」四條，變成會在 CI 紅燈的不變量。這是本次審查最重要的可交付物，也是初稿最該有卻缺席的東西。

### 讓不變量失敗成為設計對話的觸發點

當某節點的行為無法用現有能力表達，正確反應不是加特例讓測試繞過，而是停下、提出要新增的**泛型能力**、由人類確認後再繼續。不變量失敗是信號，不是障礙。

### 在寫第一個節點之前，先設計「加一個節點的形狀」

要實作什麼介面、登記在哪、哪個測試驗證它完整。這個形狀就是架構目標的可執行版本。有了它，「人類可維護」不再是文件裡的願望，而是每次 commit 被機器檢驗的事實。
