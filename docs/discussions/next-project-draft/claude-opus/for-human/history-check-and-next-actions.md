## 一、檢驗方法

我看了以下實際證據，不是憑印象：

- git 全歷史：379 次提交，2026-09-12 至 2026-09-22，共 10 天。
- 各檔案的變更次數（churn）。
- `sgrape_core.py` 在首版、中期、末期的行數與結構。
- `STATUS.md` 的交付檢查點紀錄（269 次變更，逐版交付日誌）。

以下每一條都標明：**印證**、**修正**或**細化**。

## 二、逐條檢驗

### 【印證】交付節奏極高，且每次交付都是綠燈

- 379 次提交／10 天。單日尖峰：09-19 有 111 次、09-20 有 89 次、09-18 有 59 次。
- 我先前說「單日十幾次交付」是**低估**；實際尖峰破百。
- `STATUS.md` 每筆都顯示測試通過、四份使用者 Shader 保留、SHA256 檢查點。**每次交付都是綠燈**這點完全成立。
- 判定：印證（且我原本還說輕了）。

### 【印證，且是最強的一條】力氣壓倒性地花在「正確但非核心」的方向

- 380 筆提交訊息中，**153 筆（約 40%）**是 UI／呈現主題（uniform、slider、color、glow、note、group、layout、wire、hit、arrow、appearance、geometry、touch、panel、card）。
- churn 最高的程式檔全是前端：`style.css` 123、`locales.json` 105、`graph_ui.js` 103、`inspector.js` 89、`app.js` 76。
- 對照之下核心編譯器 `sgrape_core.py` 只改了 29 次。
- 這強力印證了《價值審查》的判斷：大量精力投入在正確、但無助於「人類可維護的節點定義」這個核心目標的方向。**證據把這條從『我的觀感』升級成『可量化的事實』。**
- 判定：印證（量化支持）。

### 【修正】不是「架構在漂移」，是「架構在第一天就定型，之後只增生」

這是我最需要修正的地方。

- 我先前的講法暗示 `sgrape_core.py` 的 if/elif 是「幾百次決策累積漂移」出來的。**證據不支持這個畫面。**
- 事實：以節點 key 分派的 if/elif 形狀，**在第一天的首版就已存在**（首版即有 16 處 `EMITTER_IDS`／`elif` 命中）。這個檔案從 764 行（09-12）→ 1314 行（09-18）→ 1852 行（09-20），**一路保持同一個形狀,只是不斷加分支**。它只被改了 29 次,相對穩定。
- 所以正確的畫面不是「漂移」,是**早期定型後的骨化(ossification)**:根本形狀在第一天就決定,之後沒有任何一次任務回頭挑戰它,檔案靠增生翻倍。
- 這個修正其實讓論點**更強**:形狀不是失控漂走的,是**在唯一會決定它的那個時刻(第一天)被定死,然後因為後續任務的顆粒度永遠不會回頭質疑地基,而被鎖住。**
- 判定：修正（且修正後的版本更精確、更有用）。

### 【修正】複利的驅動力是「迭代次數」,不是「日曆時間」

- 我先前說「專案跑得夠久,漂移才複利」。但 TD-Grape 的**日曆時間只有 10 天**,不長。
- 真正夠大的是**迭代次數**:379 次提交。複利是**決策數量**的函數,不是時間的函數。
- 修正後的說法：不能用「才做沒幾天」當安全感——380 次迭代在 10 天內就足以鎖死地基。
- 判定：修正。

### 【印證】行為確實洩漏進前端

- README 自己的診斷是「節點行為與決策邏輯散落到產碼器**與前端**」。
- 前端的巨量 churn（`graph_ui.js` 103、`inspector.js` 89）印證了行為確實不只在編譯器,也漏進了 UI 層。
- 判定：印證。

### 【印證】驗收方法看得見 UI、看不見架構

- 把上面兩件事並起來看,得到一個強力印證《價值審查》第二節的畫面:
- 人的護欄注意力,**壓倒性地投在看得見的層(UI:40% 的提交、最高的 churn = 密集的人工指揮迭代)**;而架構層——使用式驗收看不見的那層——在第一天定型後,幾乎沒再被抬起來檢視。
- 核心不是被粗心遺忘的,是**驗收方法在結構上就照不到它**,所以它從沒得到護欄待遇。
- 判定：印證(這是整份檢驗裡,證據與理論咬合最緊的一條)。

## 三、修正後的完整圖像

TD-Grape 不是一個「慢慢爛掉」的專案。它是:

> 在**第一天**把編譯器的形狀定成「以節點身分分派」,然後在 10 天內用近 380 次高速迭代,把 40% 的力氣投進使用式驗收看得見的 UI 層,讓那個第一天的形狀在無人回頭質疑下增生翻倍——因為驗收方法照不到地基,地基就從沒進過護欄的守備範圍。

「漂移」是錯的詞。正確的詞是**早期定型 + 周邊高速增生 + 地基對驗收隱形**。

## 四、對「如何開始新專案」的具體含意

修正後的圖像,直接改寫了行動建議。以下每條都由上面的證據推出:

1. **關鍵窗口是第一天,不是「之後某個重構時機」。**
   證據:形狀在首版就定死,29 次改動全是同形狀增生。含意:泛型產碼器的形狀、與守它的不變量測試,**必須是第 1–3 個提交**,不能「之後再補」。等你加到第 20 個節點,形狀已骨化,補測試只會把壞形狀固化下來。這正是 Antigravity BOOTSTRAP(第一天單節點、零硬編碼)與本資料夾不變量測試存在的理由——它們鎖的是**唯一真正在決定形狀的那一刻**。

2. **用「迭代次數」而非「時間」來判斷風險。**
   證據:10 天／380 次就足以鎖死。含意:別用「才剛開始」當安全感。護欄要在迭代次數爬升**之前**就位,也就是從第一個提交起。

3. **護欄要專門守住你的驗收方法照不到的那層。**
   證據:人工驗收密集覆蓋 UI、對編譯器架構全盲。含意:外化的護欄(測試)最該守的,恰恰是**節點註冊／產碼的形狀**——因為那正是你的自然驗收永遠抓不到的層。本資料夾的不變量測試 `ENGINE_SOURCE_DIRS` 已把 `src/editor/graph` 一併納入掃描;證據支持保留這個範圍(行為會漏進前端)。

4. **第一階段明令延後 UI 打磨。**
   證據:40% 的力氣進了 UI,而核心目標(人類可維護的節點定義)沒因此前進。含意:新專案第一階段,在「節點定義 → 泛型產碼」的形狀被鎖死並被測試守住**之前**,刻意凍結 UI 打磨。Antigravity BOOTSTRAP 已寫明「第一天禁止建立 UI」——證據強力背書這條,它不是保守,是直接對症。

5. **把「地基是否還是一個地方」設成里程碑檢查。**
   證據:地基骨化是無聲的,沒有任何一次交付因它變紅。含意:除了每次 commit 的不變量測試,在每個里程碑做一次獨立複審(見《護欄與顆粒度陷阱》第七節),專問一句:「要理解任一節點的完整行為,是否仍只需去一個地方?」這是唯一能在骨化變成 1852 行之前抓到它的動作。

## 五、一句話結論

證據把我的分析**修掉了一個錯詞(不是漂移,是骨化)、補強了兩條量化事實(40% 力氣在非核心、380 次迭代/10 天),並印證了最核心的一條(驗收方法照不到架構)。**

而修正後的結論對行動更明確:**新專案的成敗,幾乎完全押在第一天有沒有把「泛型產碼的形狀 + 守它的測試」鎖對。** 過了那個窗口,後續的顆粒度就再也不會回頭救它。
