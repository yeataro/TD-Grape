## 執行摘要（Executive Summary）

本計畫書旨在為 TouchDesigner 節點式 Shader 編輯器制定一套**非破壞性、高確定性且杜絕技術債遷移**的重構推進藍圖。

當前系統已成功跑通了絕大多數核心功能與互動閉環，其真實價值在於**「已經完成功能與互動驗證」**。然而，受限於早期探索的歷史包袱，內部代碼與架構已達維護極限。

本計畫不採取傳統「在舊代碼泥潭中修補」的高風險路徑，而是採用**「以人類思維進行逆向重構（Reverse-Architecting from Proven Features）」**：
1. 將現有進度定錨為 **v0.9 Functional Prototype (FP 版)**，作為活體功能規格原型。
2. 由最熟悉實作細節的 **Codex**，在給定的大架構典範下，**假想最乾淨的架構**，逆向梳理出純淨的「物件表、API 表與使用手冊」。
3. 經由 **人類** 與 **Claude** 進行多重審閱，拍板定案理想架構規格。
4. **另立新專案**，以審定後的架構為不可逾越的「死框架（Strict Invariant Framework）」，在零代碼搬遷的前提下，將舊版邏輯乾淨重新實現為正式產品。

### 1.1 定錨意義
* **肯定歷史價值**：FP 版已成功證明產品概念可行性（Proof of Concept）與互動手感，其承載的功能細節與邊界坑洞是無價的資產。
* **卸下維護枷鎖**：既然定錨為「功能預覽原型」，就無需再逼迫人類工程師或智能體在現有失控的舊代碼中做局部的縫縫補補。

## 二、重構思維轉換：用人類的方法進行逆向重構

```
傳統失敗路徑 (泥潭修補):
[舊失控代碼] ---> 邊看爛代碼邊改 ---> 被舊思維牽著鼻子走 ---> 產生新技術債

本計畫成功路徑 (人類逆向推導):
[v0.9 FP 活體功能] 
      │
      ▼ (人類工程師最高審美)
[假想最優雅的心智模型] 
      │
      ▼ (提煉為純淨規格)
[領域物件表 + API 表 + 使用手冊] 
      │
      ▼ (另開新專案 / 剛性死框架約束)
[全新正式產品代碼 (Production Code)]
```

### 2.1 什麼是「用人類的方法重構」？
1. **脫離程式碼實作，回歸本質問題**：
   看著畫面上正在跑的功能，不看背後寫了幾萬行的條件分支，只問：
   > *「如果這套功能要以人類工程師最舒服、最直覺、最易維護的物件導向領域模型來表達，它該長成什麼樣子？」*
2. **三維度檢視架構**：
   * **呼叫與使用維度（Usage & API）**：下游開發者或外部系統調用它時，API 是否如同講人話般直觀？
   * **日常維護維度（Maintainability）**：當單一功能壞掉時，是否能一眼看出是哪個 Object 的職責，而不會牽一髮動全身？
   * **規模擴充維度（Extensibility）**：新增一個全新節點類型或後端方言時，是否只需擴充子類別或外掛，完全不用改動核心管線？

## 三、智能體協同流水線（Multi-Agent Collaboration Pipeline）

本架構重構充分利用各方特質與實際用途，建立四方（人類 + 三智能體）權責閉環：

```
+-----------------------------------------------------------------------+
| 1. 聯合架構委員會 (Architecture Council)                               |
|    - 【人類主導】使用者（核心願景、使用者心智模型、終審裁決）           |
|    - 【靈感激發與架構探索】Antigravity（快速反饋、啟發思考、物件抽象） |
|    - 【現實工程約束】Claude（收斂邊界、系統工程約束、現實落地性）       |
|    ==> 發揮各自特質，三方共同確立頂層規範與物件層級範本 (Object Archetype)
+-----------------------------------+-----------------------------------+
                                    │ (注入規範、範例與紅線)
                                    ▼
+-----------------------------------------------------------------------+
| 2. 原開發智能體 (Codex)                                               |
|    - 擁有最完整的實現歷程記憶 (Edge cases, Pipeline quirks)           |
|    - 任務：對照 FP 功能，假想理想架構，逆向撰寫《物件表、API表、手冊》|
|    - 限制：不碰舊實現代碼，純萃取規格與介面                           |
+-----------------------------------+-----------------------------------+
                                    │ (產出純淨規格書草稿)
                                    ▼
+-----------------------------------------------------------------------+
| 3. 獨立雙重審閱 (Claude & 人類審查)                                   |
|    - 依「實際檢閱用途」決策：進入內容期，著重客觀無偏見的嚴格規格檢視   |
|    - Claude 站在獨立客觀第三方視角，進行系統工程、型別契約與邊界審核  |
|    - 人類架構師進行最終審定，拍板定案理想架構規格                     |
|    （Antigravity 迴避審核，避免既出題又評分，確保審查獨立性與客觀性） |
+-----------------------------------+-----------------------------------+
                                    │ (拍板定案，固化為「剛性死框架」)
                                    ▼
+-----------------------------------------------------------------------+
| 4. 落地全新專案 (Clean Slate Implementation)                          |
|    - 另開全新專案庫，引入死框架與規格書                               |
|    - 嚴禁搬遷舊代碼，純參考舊版邏輯在新框架內從零乾淨實作             |
+-----------------------------------------------------------------------+
```

### 3.1 為什麼這樣分工？（協同哲學）
* **階段一：取各方特質（Complementary Strengths）**
  * 架構初期需要發散與靈感，同時需要強力的收斂拉力。
  * **Antigravity** 反應敏捷、能快速提供回饋並刺激架構想像力與領域抽象；**Claude** 擅長嚴謹邏輯、能強力將構想「約束回現實工程邊界」；**使用者** 則掌舵產品靈魂與直覺體驗。三方特質互補，能激盪出最完備的典範。
* **階段三：依實際用途（Objective Audit Purpose）**
  * 當規格書進到實質內容期，目標是「精準檢閱、排除盲點、杜絕偏見」，不需要過多發散視角，避免多頭修訂導致混亂。
  * 由未參與規格起草的 **Claude** 擔任獨立客觀的系統工程稽核，搭配 **使用者** 終審，能達到最高純度的審查品質。

## 四、階段一交付物規範：Codex 逆向提煉標準

Codex 的核心任務不是寫 Code，而是產出三大獨立於舊實作的純淨文檔：

### 4.1 交付物 A：領域物件表（Domain Object Catalog）
必須在「物件層級（Object Level）」清晰定義系統實體，禁止 DOM 與 UI 雜訊污染領域模型。

| 欄位名稱 | 規範說明 | 範例（以連線為例） |
| :--- | :--- | :--- |
| **Object Name** | 領域物件名稱（具體名詞） | `Connection` |
| **Layer / Level** | 所屬層級（Domain / Engine / Presentation） | `Domain Core` |
| **Core Responsibilities** | 單一核心職責（1~2 句話） | 管理兩端點的依賴拓撲關係與型別相容性驗證 |
| **Properties & State** | 內部持有的純狀態（無 UI 座標） | `id`, `sourceSlotRef`, `targetSlotRef`, `dataType` |
| **Collaborators** | 與誰互動、依賴誰 | `Slot`, `Node`, `GraphValidator` |
| **Forbidden Dependencies** | 嚴禁依賴的項目 | 嚴禁依賴 SVG Path、Canvas Viewport 或 DOM Event |

### 4.2 交付物 B：API 規範表（API Specification）
每一個物件的對外公開方法，必須如同嚴謹的 SDK 般清晰：

* **方法簽名（Method Signature）**：強型別輸入與輸出。
* **前置條件（Pre-conditions）**：調用此方法前系統必須處於什麼狀態。
* **副作用（Side Effects）**：該方法會改變什麼內部狀態，是否拋出事件。
* **後置驗證（Post-conditions）**：執行完後保證滿足什麼約束。

### 4.3 交付物 C：理想使用手冊（Ideal Usage Manual）
以全程式化（Headless / Code-first）的角度示範理想用法。例如：
```typescript
// 理想心智模型示範：不依賴任何瀏覽器 DOM 也能完整跑通一張圖
const graph = new ShaderGraph();
const uvNode = graph.createNode("TD_UV");
const noiseNode = graph.createNode("PerlinNoise");

// 優雅直觀的連線 API
graph.connect(uvNode.output("uv"), noiseNode.input("coords"));

// 純計算與產碼
const glsl = graph.compile({ target: "WebGL2" });
```

## 五、階段二審閱標準：多重審查檢核清單（Review Checklist）

當 Codex 提交規格書後，人類與 Claude 將依據以下標準進行嚴肅審查：

```markdown
[ ] 1. 領域純粹性：物件定義中是否徹底根除了 DOM、Canvas、React/Vue 等視圖依賴？
[ ] 2. 職責單一性：是否有物件承擔超過一項核心職責？（如：同時管型別推導又管字串拼接）
[ ] 3. 多載與方言收斂：是否將多載（Overload）與環境（Manifest）正交拆分，不再出現條件分支爆炸？
[ ] 4. 呼叫直覺度：API 調用是否符合現代物件導向典範，使用者手冊是否一目了然？
[ ] 5. 邊界完備性：舊版 FP 踩過的坑（如：型別降級、常數推斷、反向環路）是否在新規範中都有相應契約？
```

## 六、階段三落地新專案：在「死框架」下全新實作

```
+-------------------------------------------------------------------------+
|                        全新獨立專案 (New Clean Repo)                    |
+-------------------------------------------------------------------------+
|                                                                         |
|  [剛性死框架 (Strict Guardrails)]                                       |
|  * 階段二審核通過的 TypeScript 抽象介面與領域模型                       |
|  * 任何代碼如果違反了架構邊界，CI / Lint 直接報錯阻擋                    |
|                                                                         |
|  [實作紀律 (Implementation Discipline)]                                 |
|  * 🚫 絕對禁止「Ctrl+C / Ctrl+V」搬移舊專案代碼                         |
|  * ✅ 允許「看著 FP 驗證過的邏輯」在新框架內全新實現                    |
|  * ✅ 單節點產碼測試先跑通（TDD 閉環），再逐步組裝畫布 UI               |
|                                                                         |
+-------------------------------------------------------------------------+
```

1. **框架即律法（Strict Framework）**：
   新規劃好的物件階層與介面，在新專案中是「不可撼動的骨架」。實作者的自由度被嚴格限制在具體物件內部，杜絕任何跨層級的義大利麵依賴。
2. **邏輯移植，代碼歸零**：
   只借鑑舊 FP 中驗證正確的演算法核心（如：GLSL 生成片段、特定演算法矩陣），其餘所有物件狀態管理、事件通知全部全新編寫。
