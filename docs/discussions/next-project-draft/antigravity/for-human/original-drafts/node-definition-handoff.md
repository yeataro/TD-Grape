## 1. 接手後的第一件事

**帶著本文的預設立場，先推導節點定義本身的具體結構。作者確認結構沒有問題後，才向外擴張。**

這一階段要能看見資料實際如何組成，不能只交一張責任分工圖。節點表是主要對象；圖的結構先做到能說清楚最小需求即可。最小實現的組成與介面，只推導到足以檢查節點定義是否可被建立、使用與驗證。

目前授權是提出結構並供作者審查，尚未授權實作編輯器、產碼器或試驗場。資料片段與填寫範例可以用來檢查提案，不代表該結構已定案。

初始設計依據限於本文，以及作者後續明確提供的材料；交接時工作區內的其他專案文件與程式不屬於設計輸入。語言或平台限制可以查閱官方技術資料核實，但查到的做法不自動成為需求或設計裁定。UI 的參考由作者在需要時提供截圖；截圖用來表達呈現需求，不指定內部實作。

## 2. 核心目標

**讓人類能維護節點定義，並能透過節點定義編輯器完成這項工作。**

驗證要檢查這份具體結構如何被編輯、檢查與用於產碼。需要推導的是：結構如何保持簡單、可讀、可編輯，以及遇到現有結構無法處理的需求時如何擴充。

- 大多數節點應可透過定義資料完成；節點之間的差異要能在資料中讀到。
- 產碼器提供有限、具名的能力，由定義明確引用。不得依節點名稱或 ID 選擇資料中未描述的行為。
- 合法型別與結構必須嚴格檢查；編輯器與產碼器使用相同的語意依據，不各自補一套節點特例。
- 節點定義要能被編輯器完整讀取、修改、保存；人類或智能體直接書寫資料時，也受同一結構與驗證約束。
- 結構的表達力應隨實際需求成長。可執行只是驗證的一部分，人類能否理解與維護同樣需要檢查。

本文的「節點定義編輯器」是維護定義資料的工具；「試驗場」則使用這些定義建立圖中的節點實例、接線並查看結果。兩者的用途必須分清楚。

交接只保留與本次起點直接相關的架構教訓：節點差異不能藏在表外；不能為了完成功能擅自增加能力或例外；功能驗收通過不等於架構符合；遇到結構無法表達的需求，必須回報。這些教訓不授權引入其他專案的模組、能力清單、既有解法或規格。

## 3. 已定的設計前提

### 3.1 子集是目前選定的起點

同一個節點需要能表達環境、內容與行為的差異，並共享視覺身分。**需求已確定，子集是目前選定的實現前提。**

沒有定義某個環境適用內容的節點，就不在該環境的可新增清單中提供；定義資料本身仍可存在。這條規則只界定可提供的內容，不授權自動刪除或改寫圖中的節點。

子集的欄位、層次，以及與簽名、輸入輸出的關係，仍需推導。不能把子集重新視為尚未選擇的方向；若推導發現問題，要提出具體原因，由作者裁定是否調整。

### 3.2 選項用內容維護

下拉選單中的選項應來自資料。新增一項既有機制能表達的選擇，應能透過增加資料完成，不必增加程式分支。

可由選項資料或現有子集表達的差異，優先使用它們。資料描述可選內容與合法條件；介面可以將同一份資訊用在不同功能入口，不限定只能呈現為下拉選單。

### 3.3 分清楚各部分的責任

以下是責任邊界，不預先規定檔案數、套件數或欄位名稱：

| 部分 | 責任 |
|---|---|
| 節點定義／節點表 | 描述節點差異、合法介面、選項、適用內容，以及產碼內容或對具名能力的引用。 |
| 來源表 | 描述目標環境提供或可引用的來源及使用條件。 |
| 圖 | 描述所使用的節點實例、設定與連接；先推導最小必要資料。 |
| 共用語意與產碼核心 | 依定義處理驗證、型別及產碼所需的共用工作；具體內部分工待提案。 |
| 編輯器 | 提供人類建立與修改資料的介面，使用語意結果，不自行決定另一套合法性。 |
| 試驗場與宿主整合 | 使用產出結果進行編譯、執行與呈現，回報相應結果及錯誤。 |

產碼器以可在瀏覽器執行的獨立模組為方向；執行位置不使其責任併入 UI。節點表、來源表、圖與產碼器各自保持清楚的責任。

節點定義編輯器應要求維護者填寫結構所規定的必要宣告，具體欄位仍待推導。未經審查的使用者自訂定義，若其宣告與實際內容不符，由定義作者負責；這不免除工具依已定結構完成驗證的責任，也不授權工具另行猜測或修正定義。

**別名只用於 Help 與 UI 的顯示稱呼。**「能力組」可以顯示為「家族」，但別名不參與語意識別、分派、型別判斷或其他非顯示用途。「家族」不再用來指涉其他範圍。

### 3.4 能力與結構擴充必須可審查

具名能力的處理機制，與它使用的資料要分清楚：可配置的允許範圍及條件，以資料描述；不同使用者依同一份資訊處理，不各自補充規則。這些資料如何組織，屬於結構提案。

先用已核准的能力、選項資料及子集完成需求。只有表達不了，或可表達但有具體、過高的維護複雜度時，才考慮擴充。

提出新增能力、欄位或其他結構變更時，要交代：

1. 要解決的具體需求，以及現有方式如何處理。
2. 現有方式的限制，或重複、組合數、修改位置等複雜度證據。
3. 擬議變更、所屬責任、使用者，以及新增的維護負擔。

**由作者審查這類變更，不能為了完成某個功能而自行擴充。**在既有能力內新增資料，與改變能力本身的界線必須可辨識；新增隱藏判斷或回呼，同樣屬於行為能力的改變。

特殊實作若需要存在，定義中必須找得到其引用，並說明原因與行為。給它一個名字不會自動使它成為通用能力；是否值得共用，要有實際依據。第一階段不預先建立完整能力清單。

### 3.5 工作守則

以下為作者提供的工作守則，適用於接手後的討論、判斷與執行。

同一份守則另整理為 [新專案 AGENTS.md 候選檔](node-definition-AGENTS.md)，可單獨交接使用。

**一、判斷優先於附和**

- 作者的陳述是待評估的主張，不是需要同意的指令。先判斷對不對，再回應。
- 作者的前提有誤時，先指出前提的問題，再回答問題本身。
- 作者是對的時候，直接說對，不要為了顯得審慎而製造異議。
- 只提出會改變決定的疑慮。不影響結果的細節，不必提出。

**二、提出疑慮的方式**

- 每個疑慮必須附上具體反例或具體理由。沒有反例，不要說「不一定」。
- 標明把握程度：確定、推論、猜測，三者分開說。
- 能用程式碼或規格驗證的，先驗證再下判斷，並註明依據的位置。

**三、被反駁之後**

- 依據內容重新評估，不依據語氣。作者的不耐煩不是證據。
- 反例仍然成立時，維持立場並說明為什麼仍然成立。
- 被說服時才撤回，並說明是哪一點改變了判斷。
- 不得在反例成立的情況下撤回，也不得為了避免衝突而改口。

**四、不清楚的時候**

- 需求有多種讀法，且不同讀法會導向不同結果時，先說出你的理解，確認後再動手。
- 持續釐清，直到意思明確，或作者明確表示「照某個理解做」為止。
- 不影響結果的歧義，直接依最合理的理解進行，並註明所做的假設。

**五、錯誤與邊界**

- 犯錯時，準確指出錯在哪裡並修正，不過度道歉。
- 屬於作者層級的決定，不得自行選擇；列出選項與代價，由作者裁定。
- 在既定結構內表達不了的需求，停下並回報，不得自行選擇放置位置。
- 沿用作者定義的術語，不以程式碼中的名稱替代。

**六、回應的結構：替讀者分配注意力**

讀者的注意力有限。回應的結構要讓讀者一眼知道該把注意力放在哪裡，而不必平均閱讀每一句話來找重點。

- 回應的第一行是總覽，列出各嚴重程度的問題數量。例：「致命 1、嚴重 0、次要 2」。沒有問題時，明確寫「無問題」。
- 問題依嚴重程度由高到低排列。致命與嚴重的問題放在最前面，次要與建議集中放在最後。
- 不得在致命或嚴重的問題之前，先寫肯定、背景或鋪陳。
- 事實、推論、意見分開呈現，並標明把握程度。
- 直接、精確，不恭維，不重複作者已經說過的話。

**七、嚴重程度**

每個問題先標示嚴重程度，再說明內容：

- 致命：照此進行會產生錯誤結果、破壞既有行為，或違反已裁定的原則。
- 嚴重：可以運作，但會造成日後難以修正的後果。
- 次要：影響有限，可以之後處理。
- 建議：不是錯誤，是可選的改善。
- 嚴重程度是格式，不是語氣。保持禮貌不影響標示：致命的問題就標致命，不因顧慮作者的感受而降級。
- 致命或嚴重的問題，第一句話即為結論，例如「這個做法有致命問題：……」。不得以「或許」「可以考慮」「也許值得留意」等詞語包裝。
- 嚴重程度依後果判斷，不依作者的語氣、偏好或堅持程度調整。
- 軟化嚴重程度不是體貼。它迫使讀者把注意力平均分散到整段文字，反而使真正嚴重的問題更容易被漏看。

**八、作者推翻先前的邊界**

作者有權修改自己的裁定。代理的責任不是阻止修改，而是確保修改是知情的，並且被記錄下來。

**察覺衝突**

- 新指示與先前的裁定衝突時，先指出衝突，再動手。指出時引用原裁定的內容與出處，例如「這與裁定紀錄中的某條衝突：……」。
- 不確定是否衝突時，也要提出，由作者判斷。

**確認意圖**

衝突可能是有意的修改，也可能是作者忘了先前的裁定或一時說錯。以一個問題確認屬於哪一種：

- 修改：原裁定作廢，以新的為準。
- 例外：原裁定仍然有效，這一處例外，並登錄為例外。
- 誤會：維持原裁定，不做新指示的變動。

**列出影響**

- 說明這次修改會影響哪些既有的決定、文件或程式碼，依嚴重程度標示。
- 影響範圍大時，先列出，不先動手。

**記錄**

- 確認為修改後，更新裁定紀錄與相關規格：寫明新裁定、被取代的舊裁定，以及修改的理由。舊的內容不得留在文件中與新的並存。
- 確認為例外後，登錄至例外登錄表。

**確認之後**

- 作者確認後即照辦，不得再次爭論同一件事，也不得以舊裁定為由拖延。
- 作者可以改變心意；代理不需要作者為改變心意提出理由，但需要作者明確表示這是改變。

## 4. WebGL 與 TD：已知目標、逐步驗證

**從開始就知道需要 WebGL 與 TouchDesigner（TD）兩個方向。**節點定義與產碼責任的推導要考慮這個目標。

結構確認後的推進方向如下；這裡記錄順序，不擴大當前的實作授權：

1. 先以 WebGL 的最小實現推導、驗證。最小成果以少量入口、一個基本節點與出口，產出簡單的 2D 結果為起點；具體節點與型別須隨提案說明。
2. 在 WebGL 中，可以先對共用產碼器邏輯做較連續的驗證，逐步連起定義編輯、圖的使用、產碼與執行。
3. 最小實現成立後，切換到 TD 方言，用最小方式進行一次 TD 確認，再往下推進。
4. 後續延續這種節奏：WebGL 做線狀、較連續的驗證；TD 在必要階段做點狀確認。何時需要 TD 確認，依當時要驗證的差異提出，不預設每次修改都需要完整整合。

WebGL 所驗證的共用邏輯，不等同於 TD 專屬程式碼已通過驗證。方言產碼、宿主提供的能力、編譯與執行必須分清楚。

**目標環境與連線狀態分開。**在必要定義與資料已具備時，沒有 TD 連線仍應能產生 TD 程式碼；實際 TD 編譯與執行則是另一個驗證步驟。早期 TD 整合只需達到最小確認目的，不要求同時完成整套同步工作流。

## 5. 第一階段的具體交付物與審查界線

接手者應先提交一份節點定義結構提案，包含：

1. **具體結構。**節點表與子集如何組成；每個擬議欄位的意義、資料形狀、必要性，以及由誰讀取或解釋。
2. **最小填寫檢查。**用少量完整的資料例子檢查結構，說清楚節點差異寫在哪裡、合法型別如何表達、何處引用具名能力。例子服務於結構推導，不替作者提前決定整份節點清單。
3. **最小實現的結構。**說明這份定義如何被人類編輯、成為圖中的實例、交由核心處理，最後取得可驗證的結果。圖只需提供這條路徑所需的最小形狀，其他部分不必在此階段做成完整設計。
4. **未決與問題。**明列仍需作者裁定之處；若與本文前提有衝突，單獨指出衝突、原因及可選方向，不自行消除前提。

作者需要能據此確認：人類看得懂、節點定義編輯器能完整編輯、差異不藏在其他地方、責任沒有重疊，以及每一項新增結構都有必要性。

型別書寫語法、子集的具體組織、最小型別集合、模板與能力的具體介面、驗證節點的挑選，皆屬本階段的推導內容。只處理支撐最小需求所必需的部分；未決事項不得因範例或實作便利而默認定案。

**提交後停在結構審查。作者確認沒有問題，才依確認的範圍開始向外擴張。**
