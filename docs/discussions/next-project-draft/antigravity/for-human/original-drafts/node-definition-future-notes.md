# Grape（未定）後續目標筆記：常數傳播、更新鏈路與解釋圖

文件版本：2026-09-22.r1。專案名稱尚未定案。

**可延後閱讀，不是第一階段的實作要求。**這份文件供新對話理解後續目標；不要求先建立完整的傳播器、最佳化器或新增任何 schema 欄位。第一階段授權以[初始交接](node-definition-handoff.md)為準。

本文明確區分三種狀態：「作者已明示的目標與邊界」、「提出中的設計方向」、「審查發現與待裁定事項」。設計草案被整理進本文，不代表已獲採納。

## 1. 作者已明示的目標

作者希望使用者能從圖上理解：

- 哪些結果具備編譯期常數等性質，哪些要在執行時取得。
- 修改一個值時，哪些運算路徑涉及這個來源。
- 為什麼有些變更伴隨產碼或編譯工作，有些只更新執行時數值；這有助於理解顯示暫停的原因。

來源高亮服務於理解、顯示與選取，不宣稱是 GPU 實際逐節點執行的追蹤。編譯與執行是不同事件，也不是每次編輯都必然重新編譯。

**審查建議，尚非事件介面的設計裁定：**將性質分類、依賴路徑與實際更新事件分開提供給 UI。分類只能說明性質與適用的處理條件；「本次確實產碼／編譯／只更新參數」應由執行該工作的部分回報，不能從路徑高亮推定。尚未選定事件格式、計時或 UI 表現。

## 2. 作者已明示的工作資料與身分範圍

作者要有一份在記憶體中的解釋圖：編輯時解釋連接及語意，保留已計算的工作結果；相關編輯發生後，結果對應當前的圖。UI 與產碼核心可使用同一份語意依據，責任仍分開。

儲存用的原始圖保存作者的描述；可重算的分析結果不成為另一份持久權威。這不要求維護兩份獨立且互相同步的完整圖，也不要求從已最佳化的結果反推原始描述。

**身分以接孔粒度考慮，包含常態接孔與動態接孔。**解釋圖可以為它們配置 UUID；UUID 不必跨重建穩定，傳播鏈只在當下快照中解讀。接孔、連線與來源集合必須參照同一份有效快照，不得混用前後兩版暫時身分。

來源身分與顯示中的接孔身分如何對應，仍需具體設計。作者曾提供「節點 UUID 加接孔名稱、動態接孔持久 UUID、宣告名稱、宿主固定鍵」等草案；這些是待評估的鍵方案，不是現在就要加入原始圖的既定欄位。當下追蹤成立不等於已決定跨快照的身分制度。

## 3. 提出中的設計方向：共用依據，分開解讀

作者提出由節點定義描述每個輸出依賴哪些輸入、參數與宿主資訊，並區分依賴的是值、型別或相關資源資訊。具體欄位、記法與共用能力尚未裁定。

| 機制 | 傳遞及判斷的內容 | 用途 |
|---|---|---|
| 常數傳播 | 依來源性質、合法運算與適用環境，判定各輸出的資格。 | 產碼及常數使用位置的合法性判斷。 |
| 更新鏈路 | 依相應依賴關係聯集來源身分。 | 編輯時的來源查詢、路徑高亮與選取。 |

同一份依賴宣告可以被兩種機制使用；更新鏈路的結果不得代替常數資格或其他合法性規則。

節點定義編輯器會要求維護者填寫結構規定的必要宣告；具體欄位仍待結構審查。未經審查的使用者定義若宣告與內容不符，由定義作者負責。這個分工不授權新增其他程式輸入入口，也不要求產碼器藉通用程式分析補猜不實的宣告。

## 4. 更新鏈路的語意與邏輯檢查

**作者提出的語意是依賴路徑，不是精確數值影響。**例如 x 乘以 0，x 仍在該運算的路徑上；不需要先作代數化簡，才決定是否顯示這條路徑。

依賴的範圍仍要區分。例如固定長度陣列的長度查詢依賴尺寸，不讀元素值；改元素值與改尺寸，不應被當成同一種變更。來源鍵及這次變更所涉及的依賴面向如何表示，留待設計，不能只靠「同一個 UUID」就認定所有屬性都受影響。

### 4.1 在明確前提下，來源聯集成立

以下是邏輯檢查，不是已採用的儲存格式。前提是：解釋圖無環、來源引入點明確、每個輸出的相關依賴已確定，所有身分屬於同一快照。

```text
來源集合(輸出接孔)
  = 此輸出自身引入的來源
    ∪ 此輸出所依賴的各來源集合
```

**推論：**沿這張依賴圖走拓撲順序，聯集會收進所有可回溯的來源；收進的每個來源也都能沿依賴關係回溯。加減乘除不需要各自一套 UUID 傳遞規則。

```text
A → P → 終點
B → P
B → Q → 終點
C → Q

P = {A, B}
Q = {B, C}
終點 = {A, B, C}
```

A、B、C 在這裡代表已識別的來源，不把來源粒度重新限定為節點。共同來源去重；若要看中間的路徑，配合解釋圖已有的接孔與依賴邊，不必保存每條完整路徑序列。

### 4.2 更新時不能漏掉的條件

- 相關設定、接線、定義或環境改變後，重新取得有效解釋結果；不只是建立時計算一次。
- 分類相同也可能換了來源，不能只比較分類就忽略路徑的變化。
- 移除最後一條相關路徑後，來源應消失；另一條路徑仍存在時，來源保留。
- 每次重新分析依目前圖判斷，不累積歷來最高的不確定程度。
- 改值、改型別、改尺寸與改連接，要依它們實際涉及的依賴分辨。
- 有效性要求不等於已選擇增量引擎；小圖可以先檢查完整重算是否足夠。

**成本判斷，尚未量測：**集合與聯集本身簡單，但不是固定成本。若 P 個輸出各自保存最多 K 個來源，最壞會保存 P × K 個成員關係。尚未決定壓縮、反向索引或增量演算法，不能把「低成本」寫成已驗證的效能承諾。

## 5. 常數傳播：草案與未完成的裁定

作者曾提出以下四類作為傳播草案。這裡保留概念，不把它們升格為已核准的 enum 或單一排序演算法：

| 草案用詞 | 草案想區分的性質 |
|---|---|
| 常數 | 符合目標語言及使用位置的常數運算式資格。 |
| spec | 在目標環境的特化階段確定，且運算仍符合保留規則。 |
| uniform | 執行時才知道、在指定範圍內一致的結果；不表示一定另建 uniform 宣告。 |
| 逐次變化 | 對不同 shader 呼叫可能不同的結果。 |

來源種類、常數資格與執行一致性需要分清楚。「變量」不單獨充當分類依據，也不以當下畫面沒有改變判斷常數性。

作者亦提出：以保留常數性／保留 spec 性質的宣告，配合依賴的輸入性質計算輸出。**宣告放在哪一層、是否分輸出、依型別或選項有不同規則時如何表達，尚未裁定。**不得把「每個子集兩個布林值」直接當成已通過的完整方案。

### 5.1 已提出、不能在交接時略過的審查結果

以下項目供後續裁定；不要求第一階段一次實作完。

1. **宣告粒度必須能描述差異。**若同一子集含整數與浮點加法，兩者的 spec 保留條件可能不同。需要評估每條簽名分別宣告，或限定同一子集內條件一致，不能自行挑一種。
2. **預設不保留，不只是少一次最佳化。**若本可保留 spec 的整數 S + 1 被誤判為執行時結果，把它用作需要常數資格的陣列尺寸時，會拒絕原本合法的用途；若仍強行產出，則可能不合法。保守預設避免假陽性，仍有可用性代價。
3. **型別依賴也可能帶著 spec 性質。**不能排除陣列元素值之後，就把所有長度一律當成普通常數。尺寸來自特化時，必須保留這項資訊。
4. **型別與性質的順序不能僅寫成全圖各走一遍。**當上游常數結果決定下游陣列尺寸，下游型別需要上游的相關分析。是否使用符號尺寸、局部求值或其他方法，仍未定案。
5. **跨階段一律標為逐次變化，是保守策略的提案。**例如每個頂點都輸出相同的 uniform 值並以 flat 傳遞，不能只因跨階段就斷言各片段的值實際不同。要區分「不證明一致」與「已證明不一致」。
6. **子圖策略仍未裁定。**若產成使用者函數呼叫，其常數運算式資格有限制；是否攤平、何時攤平，以及是否支援多種形式，都不是交接時可代為決定的事。

規範依據：[GLSL 4.60 §4.3.3、§4.11、§5.12](https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.4.60.html)。該規範中的 Vulkan 特化規則不直接成為 WebGL 的能力；目標環境須分開核實。本文沒有將完整運算清單複製成專案規則。

### 5.2 保留的最小對照案例

- **固定陣列尺寸與元素值分開。**對 `uniform float values[4]`，`values.length()` 可為常數 4；修改元素值不改變長度。這支持區分值依賴與型別／尺寸依賴，不能由 Uniform 來源身分直接決定長度的常數資格。[GLSL ES 3.00 §4.1.9、§4.3.3](https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf)
- **紋理尺寸不能類推為固定陣列長度。**`textureSize(tex, lod)` 查的是所引用資源的尺寸，且受到 lod 影響；它不是 GLSL ES 常數運算式。同一紋理的不同 mip 層級可回傳不同尺寸。這個例子保留資源資訊依賴的需求，不提前設計資源追蹤系統。[GLSL ES 3.00 §4.3.3、§8.8](https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf)

以上是規範對照，未執行 WebGL 或 TD 原生編譯。更完整的合法清單，留到相應能力進入範圍時查證。

## 6. 留到需求進入範圍後再裁定

- 依賴宣告、來源鍵、一般與動態接孔在原始圖／解釋圖中的具體表示。
- 常數與 spec 保留規則的層級、預設、目標差異及需要常數的位置如何報錯。
- 執行一致性的範圍、跨階段的保守策略，以及與常數資格的關係。
- 同一子圖的多個呼叫點如何區分；打開子圖時顯示哪一次呼叫或是否顯示聯集。
- 兩個節點引用共同宣告時，編輯共同來源與選取單一引用節點要如何分別顯示。
- 宿主持續改動的 Uniform 與編輯器發起的改動，是否有不同顯示。
- 是否計算具體常數值、是否做常數折疊，以及採用何種更新與快取方式。
- UI 的高亮形式，以及產碼／編譯等實際事件如何提供資訊。

這些未決事項不阻擋先推導最基本的節點定義結構。
