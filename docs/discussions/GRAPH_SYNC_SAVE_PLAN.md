# 圖同步、暫存與 Shader 套用方案

2026-09-19，第一輪供審查提案。核對產品 0.8.114，文件基線 `c812843`。本輪只讀程式與官方文件，沒有修改產品、呼叫 TD 或進行效能實測。以下「建議」均待整合審查；時間值是試行起點，不是已確認規格。

後續 review：使用者原則認可架構方向，暫存細節繼續討論；保留方式改以「有限範圍內的增量保存」評估，取代僅保留最新及上一份完整副本的初始建議。保留時間、粒度及容量尚未定案，未授權據此開始產品實作。

## 1. 建議結論

產品原則（使用者本輪明確補充）：**非必要工作盡量不影響 TouchDesigner 的即時性；必要的圖合法性檢查、GLSL 編譯等工作可以付出成本。** 目標不是消除所有檢查或保證任何操作零停頓，而是使每一項成本有必要性、正確的觸發時機及可驗證的範圍。

現行架構的優點是 portable：部署方便、依賴少、能隨 TD 工程使用。這不表示禁止日後更改架構；使用者願意考慮瀏覽器產碼或外部服務，但本輪先比較收益、移植性及維護成本，不將口頭探索直接當作遷移指令。

保留一份可編輯的圖文件，按操作的實際影響安排工作；分開本地編輯、圖同步、復原暫存、產碼及正式套用。Uniform 即時值維持 TD Parameter 的所有權，不加入圖的同步或保存內容。

優先處理已確認的重複工作：外觀操作不走型別推導／產碼，Uniform 普通值更新不進入整圖檢查／來源全量歷史；再用合併與排程控制同步、暫存頻率。HTTP 換成 WebSocket 不會自行解決這些問題。

不要將「外觀改變」直接寫成「每次保存」。建議語意是：**外觀變更使圖文件需要同步；何時同步、何時暫存、何時保存工程，是另外的政策。** 同步本身也有成本，並不是換個名字就能省掉工作。

快速審查可先看本節、第 4 節操作表、第 7 節時機、第 13 節分批及第 15 節架構比較；其餘是追查依據與實作風險，不必逐項微調每個時間值才決定方向。

## 2. 名詞與資料位置

本節是方案中的工作定義；既有「圖的運算內容／圖文件」沿用 [用語表](../GLOSSARY.md)。

| 動作 | 發生位置與成果 | 不代表什麼 |
| --- | --- | --- |
| 本地編輯 | 瀏覽器更新工作中的圖與介面 | 尚未保證 TD 已收到 |
| 同步圖 | Python 接受指定版本的圖變更，更新 TD 內的圖資料／DAT | 不代表 JSON 檔或 `.toe` 已落盤，也不代表 Shader 已套用 |
| 復原暫存 | 把某一版本的圖寫入獨立 JSON 或瀏覽器復原儲存 | 不包含整個 TD 工程，不等於已套用的 Shader |
| 產码／驗證 | 將指定圖版本轉為 GLSL；按需要交給 TD 驗證 | 驗證失敗不應使工作中的圖消失 |
| 套用 Shader | 正式目標成功接受程式及必要設定 | 不隱含 `project.save()` |
| 保存 TD 工程 | TD 保存整個 `.toe` | 不是圖編輯或 Uniform 更新的自動副作用 |

更新 DAT 是 TD 執行中的資料更新，仍可能有 JSON 編碼、DAT 通知等成本；只有該 DAT 啟用了額外檔案同步或外部回呼時，才另有那些副作用。獨立 JSON 暫存通常遠小於整份工程，不能拿 `.toe` 保存時間推定 JSON 寫入很慢。使用者提供的經驗是「保存 TD 工程慢、保存小文字檔快」；本輪沒有量測兩者的實際毫秒數。

| runtime：`validate_material()` | 候選及正式目標都驗證，包含 force cook | 「編譯檢查」已涉及宿主編譯；不把後續套用概念化為必然要再編譯一次 |

| runtime、sources、history | 值路徑仍可做來源掃描、`checked_state()`、廣泛歷史快照；前端有全域 busy | 不能直接將現有呼叫搬成高頻訊息 |

這些是原始碼證據，尚未量測本輪路徑耗時。先前空白點擊修正的量測不能當作這次改善幅度。

## 4. 操作分類與責任

| 例子 | 改圖文件 | 圖同步／復原暫存 | GLSL／宿主工作 |
| --- | --- | --- | --- |
| 選取、平移／縮放、Home／Frame | 沿用目前不改圖的行為 | 無 | 無 |
| 節點位置、尺寸、收合、編輯器顏色、Frame 群組布局 | 是 | 合併後同步，另排程暫存 | 不推導型別、不產碼、不要求 cook |
| 專用 Comment 節點的文字、增刪及外觀 | 是 | 同上 | 不參與 Shader 運算；仍檢查其文件格式與合法引用 |
| 普通節點的標籤／註解 | 是 | 同上 | 現況會生成 GLSL 註解，採下節的註解更新政策 |
| 接線、運算節點增刪、型別、Graph Constant、影響運算的參數 | 是 | 合併同步及暫存 | 標记需產碼；維持自動套用能力，但合併重複要求 |
| Uniform 宣告／引用增刪、名稱或型別 | 依操作更新圖及來源描述 | 有 | 依宣告變更處理，不能當普通值寫入 |
| 既有 Uniform 即時值，含 TD 驅動值 | 否 | 無 | 更新／讀回 TD Parameter；TD 自行更新渲染 |
| TD 來源控制方式、紋理綁定、Spec Constant 值 | 逐項依既有契約判斷 | 只有圖的定義或引用確實改變才同步 | 屬宿主設定；可能觸發 TD 重新 cook／專門化，即使 GLSL 文字沒有變 |

不得直接用 `ui`／`params` 欄位位置分類：目前 `ui.typeMode` 影響 Auto 型別行為；Comment 的文字雖可能放在參數內，仍是編輯資訊。分類依有限、明確的操作／欄位契約，不新增模擬 GLSL 的求值器。對未登錄的新操作保守走既有完整路徑，不能誤標外觀而漏掉程式變更。

使用者提出的「只監控 JSON 大類別／區域」也是可選方法。建議先做少量粗分類（圖的編輯資訊、運算內容、宿主來源），搭配操作入口標記；不先做任意深度的欄位監控／Proxy 系統，也不依畫布上空間位置分運算相依性。未來若將資料格式實際重分區，可沿用這些分類；目前直接重排 JSON 會牽涉舊檔、剪貼簿、Subgraph 與歷史，因此不把格式遷移當作首批優化前提。欄位新增需有分類回歸，否則操作標記也會漏判。

瀏覽器負責本地互動、收集變更與顯示狀態；Python 負責接受版本、檢查允許的圖變更、產碼及排程；TD 擁有實際 Parameter、編譯／cook 與工程保存。Uniform 可撤銷的數值操作記錄屬編輯歷史，不是图文件的即時值副本；TD 自行動畫的每次數值變動不產生 Undo。

## 5. 建議的圖資料模型

採兩個用途明確的記錄，不拆成「外觀檔」與「運算檔」：

1. **工作圖文件**：瀏覽器正在編輯、TD 已確認收到的版本。允許尚未能成功產碼的內容，但必須是可解析、有界且具有有效身分的文件。作為重新開啟編輯器、圖匯出及復原暫存的來源。
2. **最後成功套用的快照與產物**：維持既有成功 Shader、圖／manifest、診斷對照及回復資料的責任。失敗不能覆蓋它；「重新載入已套用圖」仍指這一份。

建議以獨立、受管理的工作圖 DAT／envelope 承載第一項，保留現有成功 state 的語意，避免把未完成草稿塞進原本要求可編譯的 state。確切 DAT 名稱、schema 版本在實作審查時固定；本提案不建立 DAT。新資料隨 `.toe` 保存，JSON 暫存另外排程。

兩份記錄增加少量儲存及版本處理成本，但能明確處理「圖已同步、Shader 未套用」。如果只在編譯成功後才能留存圖，就無法完整支援這個狀態。

最低限度追蹤：圖文件版本、其中運算內容的版本，以及最後套用的運算版本。外觀同步只推進圖文件版本；Uniform 值不推進兩者。另記每個復原儲存目的地已完成的圖版本，不因收到同步 ack 就宣稱已暫存。

## 6. 外觀操作的短路徑

建議建立共用的外觀交易入口，由既有拖動、收合、尺寸、Frame、筆記 UI 使用；運算交易仍沿用既有 Auto／常數／接線檢查。

- 拖動中只更新本地顯示；完成手勢後記錄一次外觀交易及 Undo。能記位置差異就不為此複製整張圖；既有運算操作的完整快照先保留，不一次改寫全部歷史。
- 待同步外觀內容按「圖／子圖 ID、節點 ID、欄位」合併為最後值。Undo 不合併成同一筆：使用者撤銷步驟與網路批次是不同目的。
- Python 僅接受列明的外觀命令及欄位，不信任客戶端一句 `layoutOnly:true`。檢查 Shader 身分、圖版本、ID、值形狀／大小、Frame 成員等；拒絕夾帶接線、宣告、型別或任意路徑。
- 同一批次建立一次必要 ID 索引，不對每個節點重掃所有節點；複雜度目標 O(N+k)，N 是圖大小、k 是本次變更量。整個 DAT 序列化仍是 O(文件位元組數)，只在批次提交時做，不宣稱同步 O(1)。
- 純外觀的回覆只帶版本／確認資訊，不回傳來源全表、不主動抓預覽、不清掉仍有效的編譯錯誤。更新受影響節點／接線幾何；不因同步成功重建左側節點庫。
- 純選取／導航繼續走現有 UI 路徑，不為了統一交易而新增圖同步。

單純減少全圖 render 是相關收益，不以此輪名義全面重做 DOM 或狀態管理。

### GLSL 註解的處理建議

普通節點標籤／註解先同步為圖文件資料，不因編輯它就自動套用 Shader。下次明確檢視／匯出生成的 GLSL、手動 Apply 或正常運算變更產碼時，生成最新註解。

這會使 TD 目前正在使用的 GLSL 註解暫時較舊，但執行程式不變；此差異需審查接受。診斷行號仍對應「實際送去編譯的產物」，不能拿新註解的行號解釋舊錯誤。這個方案比新增一套去註解後判等的 GLSL 解析器簡單；不以正規表示式刪註解來判斷程式等價。

## 7. 同步、暫存與套用的排程

以下為建議試行值，非引用其他產品的內部數字；實測後才決定。全部只在有待處理變更時掛排程，沒有變更就不掃描／寫入。

| 工作 | 建議時機 | 合併及確認 |
| --- | --- | --- |
| 本地顯示 | 互動當下 | 沿用手勢預覽 |
| 圖同步 | 完成操作後延遲 650 ms；持續完成新操作時最多等 2 s | 一筆在途、一份合併中的新變更；不截取尚未完成的拖動 |
| 瀏覽器復原草稿 | 完成操作後延遲 1 s、持續編輯最多等 5 s | 初版沿用 sessionStorage，合併序列化；顯示寫入失敗，不聲稱跨瀏覽器保存 |
| TD 端 JSON 復原暫存 | 已同步且有新版本，安靜 5 s 或自上次成功寫入最多 15 s | 批次寫入尚未持久化的增量與必要檢查點；沒有新版本不重寫 |
| 自動產碼／套用 | 運算變更完成後沿用 650 ms 合併窗口；先取得相應同步確認 | 不在同步完成後又固定多等 650 ms；不因外觀變更排新的編譯 |
| 手動 Apply | 先 flush 必要圖變更，再驗證／套用指定版本 | 不是等待 JSON 備份完成才准套用 |
| 保存 TD 工程 | 使用者明確要求 | 先確認本分頁已完成的圖操作同步到 TD；不順帶套用未驗證草稿 |

低頻暫存有取捨：突然終止時可能損失最後一段尚未寫出的編輯。sessionStorage 合併也會改變目前「每次提交立即寫草稿」的保護窗口。以上延遲及可接受的損失窗口需一起審查；不以省效能為理由悄悄降低保護。

瀏覽器切換 Shader／載入另一張圖時先保存本地草稿並处理必要同步；不要只依賴關閉分頁事件才補救，行動瀏覽器終止不能保證最後一個請求送達。這裡不加入多人協作協定。

```text
操作完成(edit):
    若只是本地視圖：返回
    若是既有 Uniform 即時值：送值更新；返回

    將圖變更記入本地交易與 Undo
    合併待同步內容；排程圖同步
    排程本地復原草稿
    若 edit 可能影響運算：累積「需套用」狀態

TD 接受一批圖變更(batch):
    檢查身分、版本及文件／命令邊界
    更新工作圖與版本；回覆「已同步」
    標記該圖有新版本可供 JSON 暫存
    # 此處不因純外觀變更產碼、cook、抓預覽或保存 .toe

套用指定版本(snapshot):
    檢查圖與來源契約，生成 GLSL
    驗證候選；成功才套用正式目標
    保存成功產物與其運算版本
    失敗則保留工作圖與最後成功的 Shader

暫存到期：批次寫入已同步的待存增量／必要檢查點，完成後確認其版本
```

待處理的運算影響必須累積。先改 Constant、再移動節點，不能因最後一筆是外觀而跳過套用。舊請求完成也只能確認它實際處理的版本，不得清掉其後的新操作。

## 8. Uniform 通道的邊界

延續 [Uniform 連續編輯評估](UNIFORM_LIVE_EDITING.md)，這次方案先固定與圖流程的接口，不重新假設需要替換使用者 Binding。

- 圖擁有 Uniform 的宣告／引用，TD 擁有即時值與控制模式。現存初始化預設值不當作即時值回寫目標；其後續歸屬另審，不自動移除舊資料。
- 普通讀回只更新需要顯示的值與模式。無相關欄位需要顯示時，TD 的時間／CHOP 等輸入照常執行，編輯器不用為圖保存接收數值。
- 值寫入回覆來源 ID、實際結果及必要版本，不傳整圖。只驗證本次允許的 Parameter／分量，不為每個值包做全量來源匹配、圖產碼或全圖歷史快照。
- 值操作可有獨立 Undo；記錄實際改過的分量 before／after 與身分。連續手勢一筆 Undo，TD 自行更新不記；不能撤銷同時發生的他人修改。
- 普通值更新不切換全域 busy、不鎖住無關按鈕。若同一來源被刪除、改型、切換控制權或正被套用重建，才暫停／拒絕受影響值寫入。
- 權限及值操作資格不能只看「整張圖是否 dirty」；外觀尚未同步不應鎖住所有 Uniform。尚未建立或身分失效的來源仍不可寫。
- 來源結構變更偵測與值回讀分開。首次載入、來源編輯／明確刷新及需要處理外部結構變化時才做結構工作；背景偵測保留有界頻率，不把每個值更新當全量掃描機會。
- 保存 state 損壞保護仍須存在。不得刪除 `checked_state()` 後任意寫值；需建立載入時驗證、目標／來源身分核對與外部 state 改動失效規則。可先在手勢開始檢查，避免每個 update 產碼；原始 DAT 被手改或替換的可靠偵測必須驗證，不能靠永不失效的快取。

WebSocket、手勢 begin/update/commit、背壓與斷線行為沿用既有提案作後續獨立批次。先拆掉高頻路徑中的整圖工作，再評估傳輸改造；不是將改用 WebSocket 當成這輪圖同步完成的必要前提。

## 9. 主執行緒、同步 API 與背景寫檔

TD 並非所有內部工作都只有一條執行緒；對本案關鍵的是 OP／Parameter 存取、界面及相關 cook 的主執行緒。官方要求其他執行緒避免讀寫 TD 物件。普通 Python I/O 可以移到工作執行緒，但同步 I/O 寫在 `async def` 裡仍會阻塞執行它的執行緒。[TD Python threading](https://docs.derivative.ca/Python_threading_in_TouchDesigner)、[Thread Manager](https://derivative.ca/UserGuide/Thread_Manager)

| 做法 | 工作範圍 | 方案中的判斷 |
| --- | --- | --- |
| `dat.text = ...` | 更新 TD 資料，可包含整图 JSON 編碼與 DAT 通知 | 在主執行緒批次執行；不等於寫外部 JSON |
| TD `DAT.save()`／File Out DAT | 將 DAT 內容寫成普通檔案 | 適合作為簡單對照；官方 DAT.save 文件未承諾非同步完成，不先認定它不阻塞 |
| 主執行緒 Python `write_text()`／`open().write()` | 寫普通 JSON 檔 | 不因使用 Python 就變成非阻塞；小檔可能快，仍有單次等待 |
| 背景 Python 工作者寫普通檔案 | 工作執行緒等待檔案 I/O，完成後回報 | 建議的 JSON 暫存候選；只接受不含 TD 物件的快照 |
| `project.save()` | 整個 TD 工程 | 保留明確操作，不放到背景執行緒碰 TD API，也不作自動圖暫存 |

DAT.save 的用途及回傳路徑見 [DAT Class](https://docs.derivative.ca/DAT_Class)；工程保存另見 [Project Class](https://derivative.ca/UserGuide/Project_Class)。兩者不共用效能結論。

背景暫存建議只用一個有界的檔案寫入工作者，或適合現有部署的單一 Thread Manager 工作；不為每個圖／每次輸入生新執行緒。主執行緒交出指定版本、與 TD 物件隔離的不可變增量批次或完整檢查點；工作者寫入普通檔案，再回傳成功版本。完整檢查點／索引採同目錄暫存檔替換，增量格式須能辨識未完成的末筆紀錄。JSON 編碼成本也要計入，不因 I/O 已移走就忽略它。

每個圖一次處理一批寫入，待寫增量保留版本順序，限制活動圖數與佇列總大小；舊完成結果不能標記新圖版本已備份。保留歷史時不能只留下最後一份值、丟掉所承諾保留的中間版本；可以合併磁碟寫入批次，但保留點的粒度另訂。若寫入持續落後，須限制接收、回報延遲或明確降低保留粒度，不能無界堆積或默默斷開增量鏈。寫入完成不等於保證斷電下資料一定落在硬碟，是否額外 flush／fsync 是成本與耐久性的獨立取捨。

主執行緒不等待檔案 Future 或 join。停止、換工程、路徑改變時以工作／專案身分隔離結果；不能讓舊工程工作覆蓋新工程的復原檔。慢磁碟／防毒／雲端同步目錄可能使尾端延遲增大，因此要同時測一般與慢寫入情境。若簡單同步小檔寫入在目標硬體已足夠，可在審查後選較簡做法，不為假設中的瓶頸硬加框架。

CPU 密集的 Python 產碼不因換成 thread 就自動變成無成本；Python 3.11 的 GIL 也限制 CPU 工作的執行緒並行。[Python threading](https://docs.python.org/3.11/library/threading.html) 本輪先減少不需要的產碼、合併相同版本需求；不先導入外部編譯服務／子程序。

主執行緒排程先設工作數與「開始下一筆前」的時間預算，不能把它誤稱為可搶占已開始的 cook／Python 呼叫。單筆過長仍需縮小或移出可移出的工作；強制 Shader 編譯及 `project.save()` 不承諾無卡頓。

## 10. 暫存媒介與復原

建議 TD 主機的專用子資料夾 JSON 為跨瀏覽器可取回的主要復原副本；資料只包含圖文件、必要來源描述、版本、專案／Shader 身分、時間及格式版本，不掃描／快照所有 Uniform 即時值。不將 Shader 快取產物或所有歷史一起每次寫入。

### 有限範圍的增量保留（依後續 review 調整）

- 以完整圖檢查點作起點，期間批次保存按版本排序的變更；復原某個保留點時從其前方檢查點重播到該版本。
- 優先共用擬議同步交易已提供的欄位／節點變更，不另做每幀全圖 diff。不把純 Uniform 值、游標移動或未完成手勢放入圖暫存。現行所有操作尚未提供完整增量，因此共用程度仍需在實作時核對。
- 運算編輯、刪除、Undo／Redo 的變更必須足夠重建圖；不直接把記憶體內 Undo 物件序列化成長期格式。匯入／整圖替換可直接建新完整檢查點，避免為了增量反而花更多時間計算差異。
- 保留範圍可由時間、保留點數與容量共同限制，具體值待定；定期建立新檢查點，限制復原重播長度。刪除過期資料前，先確保最早保留點仍有完整可用的起點，且新檢查點已成功保存。
- 寫入量有機會很小，不能因此稱為零成本：仍有變更編碼／寫入、保留窗口整理、檢查點及復原重播。這些成本應有界並避開高頻 TD 主執行緒工作，不作為排除增量保留的理由。是否比小圖的週期完整快照更划算需量測。
- 網路同步可合併、磁碟寫入可批次、復原保留點可有不同粒度；這三者不必一一對應，也不預設每個滑鼠事件都能回到。

瀏覽器現有 sessionStorage 可先保留並合併寫入；IndexedDB 的跨重新啟動復原屬下一級能力，不因先前詢問 Cookies 就直接採用。Cookie 不作圖資料儲存。暫存路徑、無名／唯讀工程的 fallback、複製工程的身分規則以及保留天數，列為實作前少量待定政策；不得自動改写任意使用者 JSON。

暫存可保存「語法／接線尚待修正的工作圖」，不等於允許無效 JSON、重複身分或不受支援格式進入正式成功 state。載入時列出復原版本並讓使用者選擇；不默默覆蓋 TD 現有圖或部署暫存 Shader。

「已同步」「復原檔已更新」「Shader 已套用」「TD 工程已保存」在內部與回覆上分開。UI 可用簡短主狀態加細節，不需同時擺四個狀態燈；文案另審，避免擴大到先前未批准的英文全面修訂。

## 11. 衝突、失敗與相容

- **圖版本競爭**：沿用預期版本核對。不同分頁的過期變更明確拒絕，保留本地草稿；第一版不做無聲的多人自動合併。純外觀 patch 也不能跳過版本檢查。
- **請求結果不明**：批次有請求 ID，短期有界地記住結果；重送不多建版本／Undo。超時不等於沒成功，先查結果或重新核對，不重播舊值。
- **套用途中又移動節點**：套用回覆只更新實际套用的運算版本，不用舊整圖覆蓋新布局；運算版本未變時，外觀同步不讓有效的編譯白做一次。
- **套用途中又改運算**：保留新操作並再合併排程；若驗證尚未正式提交且依賴已過期，丟棄候選，不部署舊版本。來源控制模式／目標 OP 改變也須重新核對。
- **來源同步**：TD 外部新增／刪除／改名的結構變化仍需反映為圖的來源描述；不得拿「Uniform 值不改圖」取消這種同步。
- **失敗隔離**：JSON 暫存失敗不撤銷已成功同步／套用的狀態；編譯失敗不刪除工作圖；圖同步失敗保留本地修改並停止對不確定版本套用。
- **Undo／Redo**：外觀只重播外觀；運算編輯才重啟相關檢查；值歷史只重播指定 Parameter。不把已入列的較新同步於 Undo 後再寫回來。
- **舊檔／舊頁面**：保留原成功 state，沒有工作圖資料時以成功圖初始化工作副本；新舊 API 做能力／版本握手，不能允許舊頁面繞過新工作圖版本而覆蓋內容。需按既有 review 規則升級，保留未知欄位及原文，不靜默修復。
- **損壞資料**：既有成功 state／manifest 損壞仍進保護模式。工作圖的可編譯性錯誤與原始保存資料損壞是兩種狀態，不能都當作普通草稿放行。
- **來源預設值／工程保存**：初始化值的舊相容行為先保留；按 Save TD 時若圖未同步成功，要明确失敗而非显示「全部已保存」。用户直接在 TD 保存工程，只保存當時 TD 已持有的內容，無法替尚未送達的瀏覽器內容保證。

## 14. 驗收與量測

同時量測三件事：**總工作量、TD 主執行緒單次／單幀佔用、完成延遲**。平均 FPS 好看不足以證明無停頓；降低請求數也不足以證明單次工作變短。

| 情境 | 必須成立的行為／計數 |
| --- | --- |
| 移動單節點、100 節點選取、多次調整／收合 | 拖動途中零圖同步／磁碟寫入；完成後按批次同步；前後端零產碼、零 native validation／強制 cook |
| 專用筆記、Frame、標籤、`ui.typeMode` | 正確分流；不能只根據 `ui` 一律略過；生成註解及診斷行號符合提案政策 |
| 改 Constant → 移動 → Undo → 同步／套用回覆 | 不漏運算變更、不把布局回滾、不讓過期排程覆蓋 Undo |
| 編譯失敗後繼續排版、刷新／復原 | 工作圖保留，最後成功 Shader 仍運作；錯誤不因單純移動消失 |
| 已有 Uniform 從瀏覽器／TD 變動，含 `uAbsTime` | 圖內容、圖版本、復原檔寫入次數不因純值變更而改變；不產碼、不新增圖 Undo |
| 1／100／200 個來源，只改一個值 | 比較每次更新的來源讀取數、歷史資料量、Python 時間；避免值路徑隨全部來源反覆掃描，尤其 N² 查找 |
| 持續操作、慢網路、丟回覆／重送 | 同步與備份佇列有界，最終版本正確；不回覆未完成的持久化 |
| 慢磁碟、寫檔失敗、關閉／換工程 | 主執行緒不等背景 I/O；前一份有效 JSON 保留；舊工作不覆蓋新專案 |
| 增量保留窗口裁切、檢查點替換失敗、末筆寫入中斷 | 保留範圍內版本能還原；不刪除仍被依賴的起點；重播不產碼、不改 Uniform；損壞尾筆不破壞先前完整紀錄 |
| 無修改閒置、純導航 | 不因本功能定時產碼、同步或寫檔；既有預覽活動分開記帳 |
| 損壞 state、改名／刪來源、多分頁、舊版本 | 原有權限、控制模式、版本衝突及原文保護維持；不能以效能優化繞過 |

瀏覽器記錄交易、序列化、局部／完整 render、請求數、bytes 與互動延遲；TD 分別記錄來源掃描、Python 產碼、DAT 編碼／更新、native validation／cook、暫存排隊與檔案完成時間。背景計數不以每幀掃描整張圖實現。

先使用相同圖及步驟做修改前後對照，再於主電腦、副電腦／行動裝置區分 UI 與 TD 耗時。目標是純外觀及普通值更新的主執行緒成本明顯降低且不出現可察覺新增停頓；具體毫秒門檻依基線及目標刷新率訂定，不先保證所有硬體 120 FPS。背景寫檔評估需同時報 JSON 編碼耗時，不能只報 worker 的 I/O。

既有回歸入口包括 `tests/unit/test_saved_state.py`、`test_history.py`、`test_sources.py`，瀏覽器的 `test_input_history.cjs`、`test_type_drafts.cjs`、`test_reload_applied_graph.cjs`、`test_native_sources.cjs`，以及 TD 原生來源／歷史測試。新增測試聚焦跨層不變條件與實際呼叫計數；本輪文件提案沒有執行這些產品測試。

## 15. 架構選項與升級條件

| 方案 | TD 即時性可能受益處 | Portable／維護代價 | 本輪判斷 |
| --- | --- | --- | --- |
| 保留現行內嵌 Python＋瀏覽器，依變更分流 | 直接刪除外觀／普通值更新不必要的整圖工作 | 不增加安裝依賴；仍需修正資料與版本契約 | 優先方案，有直接原始碼證據支持 |
| 將產碼放入瀏覽器 Worker，TD 接收 GLSL 與必要 manifest | 將 Python 產碼／部分圖檢查移離 TD 主執行緒 | 可以仍隨產品攜帶，不必然降低 portable；但需移植或封裝現有 Python 核心、維持型別／來源契約一致，可能增加下載體積及啟動成本 | 若必要運算變更的產碼仍是主要耗時，值得另做對照原型 |
| TD 外的本機程序負責產碼／服務 | 可隔離 Python CPU 工作與網路服務生命週期 | 可打包但多一個程序、部署／啟停／版本及連線管理；CPU／記憶體仍共享，不保證宿主完全不受影響 | 若瓶頸包含持續服務及 CPU 產碼，才比較整體收益 |
| 在 TD 程序內加 Python 工作者處理所有產碼 | 可移走部分等待 | TD 物件不能跨執行緒、核心共享狀態須隔離，CPU 仍受 GIL 等限制 | 不視為一鍵完成的極端優化；先只處理普通檔案 I/O |

瀏覽器產碼若在 UI 主執行緒執行，可能只是把 TD 停頓搬到平板／手機介面，因此候選應包含 Worker。也不應平行維護兩套容易分歧的產碼器；是共享同一規格生成、移植核心，或攜帶相容執行環境，需先量測與評估，不在本輪選技術棧。

即使產碼移出 TD，宿主仍須確認被操作的 Shader 身分、來源／manifest 契約與版本，並進行實際 GLSL 編譯及參數接合；「TD 只接收」不等於接受任何外部訊息就任意改 OP，也不需要為此重做一次完全相同的圖產碼。

升級架構的依據：先分別量出必要圖檢查／產碼、來源處理、序列化／I/O、TD 原生編譯／cook 的時間占比與最差停頓；只有移走的工作確實占主要成本，才用同一圖比較替代方案。若主要成本在 TD 原生編譯，搬 Python 產碼不會解掉那部分。這不是永遠維持現狀，而是避免靠直覺換架構後仍保留真正瓶頸。

## 16. 待審查項目

架構方向已獲原則認可，尚待整合的細節包括：註解生成時機、同步／暫存延遲、有限增量保留範圍與恢復方式。暫存目錄及無名工程政策可在 D 批前定案；討論完成前不把原則認可擴大成產品實作授權。

瀏覽器持久 IndexedDB、多人即時合併、產碼搬移、完整圖歷史封存及重做整套 UI 狀態管理均非目前已有證據所要求的首批解法。架構搬移保留第 15 節的評估入口，不把 portable 當成禁止更改架構的永久限制。
