# 自含式圖封存提案

2026-09-18 使用者在矩陣開發期間提出的其他功能筆記。狀態：待評估，未實作。使用者明確排為低優先、最後再處理；不納入本輪矩陣功能，也不因記錄而改變目前匯出格式。

## 使用者意圖

一般圖 JSON 保存圖資料，內建節點透過定義 ID 與版本雜湊引用實作。使用者希望未來即使原本的節點庫已不可得，仍有足夠內容重建圖；以「三十年後仍有人想使用」說明長期保存的目的，而不是要求保證任何未來環境都能直接執行。

使用者進一步確認：即使 TD-Grape 編輯器程式本身已不存在，理想上仍能根據檔案中的完整結構、內容與語意另寫建構器重建。核心目的為「建構器可以重寫，圖的必要知識不能隨原程式消失」。因此封存需要可理解的節點行為／實作與格式語意，不能只保存仍需向原程式查詢的 ID；宿主提供的能力與相依也需要明確記錄。

- 假使未來提供沒有外部來源的圖內自訂節點定義，它的必要內容必須隨圖保存。現有隨圖保存的 Subgraph／手寫 GLSL 不能因此退化成只有引用。
- 匯出可另提供「打包所有節點」選項。較精準的候選名稱為「打包所有相依定義」或「自含式圖封存」；名稱尚未定案。
- 選用完整打包時，保存這張圖實際引用的節點定義、其實作與遞迴相依內容，以及使用時的版本。不是把整個未使用的節點庫全部複製進圖。

## 設計時需要釐清

只保存 ID、接孔、預設值與 UI 外觀，無法重建節點如何產生 GLSL。封存範圍需辨識 catalog 定義、compiler emitter、Library Function、圖內定義等不同實作來源；必要時還需可重建版本的編譯工具與格式說明。這些是後續可行性評估，不是已批准的具體打包方式。

另需決定是否附產生的 GLSL、執行環境版本及外部资源清單。TD OP、TOP／DAT／CHOP、貼圖或外部檔案是否一併打包，是與節點定義封存不同的範圍，尚未決定。完整定義封存能降低對未來節點庫的依賴，不能單獨保證 TD／GLSL／驅動等外部環境永遠相容。

匯入時如何識別並使用封存版本、與目前已安裝的同 ID 定義共存、何時可明確升級，也留待此功能正式排程時設計。
