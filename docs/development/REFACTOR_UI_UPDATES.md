# Refactor 後續計畫：核心先完備，再接入 React／React Flow

更新：2026-10-06。**方向已確認；本輪交付計畫書，正式遷移尚未開工。** 本文件是這條主線唯一的執行與進度入口，取代本文件前版的 UI-0～UI-4 次序。正式可用版本仍為 [STATUS](STATUS.md) 所記錄的 Refactor.14，不能把評估頁當成新版產品。

## 1. 本次決定與計畫的地位

人類完成隔離評估後，判定 React／React Flow 足以支援遷移，收益在於把成熟的畫布、呈現與互動能力交給框架，將開發心力放回 Shader 產品、節點及清楚的責任分工。**不是宣稱前端效能從此不用驗收，也不是把評估版整包轉正。**

本次確認：

- 後續以前端 React、畫布 React Flow 為遷移方向。Vue 不再是這條主線的待選方案。
- 先整理並完善我們自己的核心與應用能力，讓新前端透過清楚的 Interface 使用；節點路徑完成後，再討論及推進面板。
- [評估版](../../../work/refactor/react-flow-evaluation/README.md)留在原地供行為對照、問題重現與必要試驗；不搬成正式入口，不繼續以外觀細節擴大實驗。其配色、簡化歷史、探測選項與轉接寫法不自動成為正式設計。
- 本次只寫計畫與同步共識入口，不安裝正式依賴、不改產品程式、不部署 TD、不改版號。下列步驟與驗收是實作者提出的執行計畫；面板細節與中途人類測試使用新／舊入口仍待後續討論。

**用語：** 本次所說的「後端」主要指不依賴顯示框架的 TypeScript 核心，以及協調編輯、歷史與交付的應用層；它們仍可在瀏覽器執行。不是要求改成伺服器產碼，也不是把規則搬回 TD Python。TD 宿主是另一個明確角色。

## 2. 必須守住的核心價值

權威依據為[目標架構與核心價值](../../../work/in-place-refactor-design/target-architecture.md)及[正式工作流程](../../../REFACTOR-WORKFLOW.md)。本計畫將其落成以下交付條件：

| 價值 | 在本次重構中的要求 |
| --- | --- |
| 產品能力、效能與使用者體驗最優先 | 完成使用者工作才是成果；保留固定 Legacy 的最終能力目標及已確認的行為修訂。外觀、操作手感、易用性、回饋與資料安全均須驗收，不能以換框架代替交付。 |
| 嚴格模組化與單一責任 | 節點特有規則集中在節點模組；共用能力有共同實作。一般新增節點不需修改 renderer、compiler 或宿主的節點名稱分派。不以拆檔、物件數或抽象層數當作完成。 |
| 效能與低待機負擔 | 無關介面不因一次值更新被應用程式全部刷新；編輯器閒置不持續掃描／重畫。沒有編輯者時，不讓 TD 表演工程承擔不必要的同步與預覽工作。比較絕對耗時、尾端延遲及實際影響，不用百分比誇大小差異。 |
| 可理解、可維護、可追蹤 | 命名、文件、來源與生成物、TD 組件安排清楚；問題可追到操作、負責模組與失敗階段。UI 美觀屬使用者體驗；工程組織的審美也重要，不能把「產品優先」當作任意堆放的理由。 |

硬性邊界：

1. **核心不依賴 DOM、React／React Flow、TD API、Python compiler 或舊圖匯入器。** 接線合法性、型別及產碼只有一份規則。
2. **一份可寫作品狀態。** 新畫布中的 nodes／edges 是顯示投影與暫態操作資料，不另養一份可獨立修改的 shader 圖。節點座標可以保存，React 元件、DOM 尺寸、手勢時鐘與訂閱不得混入作品。
3. **既定型別政策不變。** 輸出由使用者選定；合法的本節點輸入配對與 Edge 轉換按現有規則处理，不恢復 Auto 長鏈改型，不順便擴大轉換表。
4. **圖預設值、TD 即時值與原生 Parameter 分清。** 沿用既有歷史、Expression／Export／Bind、外部改值及晚回覆保護。共用數值控制項不代表所有數值共用同一提交時機。
5. **Family 對 Manager 只有編輯依賴。** 主節點不在時，參數、既有綁定、texture 與原生 Shader 更新／執行保留；不增加搜尋、重連或重試負擔。主節點回來能恢復編輯。MAT／TOP／未來 ISF 同樣遵守。
6. **main 與固定 Legacy 只讀，IconGen → icon 保護不變。** 宿主端仍以 TD 慣用做法為偏好，實際能力、效能與 UX 決定手段；不因換前端推倒已合格的 Manager／Editor Service。

## 3. 起點、證據與缺口

以下是本輪讀取來源與評估結果的整理，不是完整能力盤點。RF-1 需把各個待接入功能補到可追蹤清單。

| 範圍 | 已有且應優先重用 | 下一步要核對／補足 |
| --- | --- | --- |
| 節點 SDK／模組 | [NodeModule／NodePresentation](../../src/core-ts/node_module.ts)，53 普通＋3 結構模組；接孔、配置、命令、驗證與產碼已有共同入口 | 顯示契約仍部分化；選項是否能明確查詢、特殊 Title／Body 如何宣告、控制項身分／綁定是否足夠 |
| 圖、接孔與線 | [GraphDocument／Network／Node／Port／Edge](../../src/core-ts/graph.ts)；子圖生命週期、交易與接線規則已有實作 | 正式 UI 各操作能否走同一入口；不能把評估版的簡化 model 當作完整應用層 |
| 變更資訊 | [GraphChanges](../../src/core-ts/changes.ts) 已有 node／port／edge／definition 層次 | 目前仍包含快照比較與保守 complete=false 路徑；顯示投影、訂閱與宣告更新需盤點，不宣稱已 O(1) |
| 產碼與目標能力 | [TypeScript compiler](../../src/core-ts/top_compiler.ts) 已供已遷移 TOP 能力使用，新宿主接收前端產物 | 自訂 GLSL、Texture／Sampler／TOP Input、array／複合型別、MAT／Vertex 等缺口按依賴補齊；不能用篩掉節點的清單冒充完整支援 |
| 現有 editor 接入 | [editor_contract](../../src/core-ts/editor_contract.ts) 與建置資料已服務舊 UI；正式 Refactor.14 能完成限定 TOP／Uniform 單次更新閉環 | 這份相容投影不是新前端永遠必需的 SDK；需逐欄判斷保留、替代或移除，避免新 renderer 再依賴舊 app 全域狀態 |
| 舊顯示架構 | CanvasUpdate 已保留部分卡片，面板排版有部分封裝 | 舊 render／Inspector 仍有跨區更新與節點特例，線仍有整批更新；核心物件化不等於顯示完成 |
| React Flow 評估 | 52 種可獨立建立節點、102 節點／101 線、值／型別／接孔、接線、簡化歷史、產碼與共用樣式已試用 | 缺完整 TD 往返、產品歷史、面板、保存、特殊節點與完整平台驗收；良好手感不等於全產品效能結論 |

评估版已證明的分工：

- 真正的節點模組、圖與 compiler 可以直接被另一套顯示實作使用；沒有為框架另寫 shader 規則。
- 共用控制項、接孔、正式線與臨時線可以引用同一顯示意圖；樣式污染曾顯示出作用範圍必須明確。
- Body 拖曳、命中及 Snap to Grid 可使用框架能力，正式位置仍走原模型入口。
- 150ms 阻尼曾因中間視口重設手勢基準而吃位移，已修正；這是前端轉接風險，不能藉修改核心語意掩蓋。
- 仍有圖快照、投影掃描與特殊能力缺口，不能把「框架接手 DOM」解讀為所有成本已消失。

評估證據與限制集中在其 README；本計畫不複製所有量測紀錄。人類已認可遷移能力足夠，不再為選 React／Vue 無止盡重做評估。

## 4. 目標責任與依賴方向

```text
節點模組 ──提供── 接孔／規則／命令／顯示意圖
                       ↓
核心圖模型與產碼 ← 應用層：作品、操作、歷史、交付協調
                       ↑                  ↔ TD 宿主 Adapter
              前端 Adapter／顯示投影
                       ↑
       React 控制項／React Flow 節點、接線與畫布
```

箭頭表示調用與資料轉接，不表示每次操作都必須產碼或送 TD。不得形成「核心先叫 UI 更新，UI 才完成規則」的反向相依。

| Module／責任 | Interface 應提供什麼 | 不承擔什麼 |
| --- | --- | --- |
| 節點模組 | 自身能力、有效接孔、可選配置、專屬命令、顯示需求與產碼 | DOM、History、React 元件、傳輸及宿主直接寫入 |
| 圖／Port／Edge／compiler | 規則、驗證、圖交易、依賴與產物；穩定身分及結構化診斷 | 面板名、刷新函式、畫布座標量測、框架狀態 |
| 應用層 | 活躍作品／scope、操作入口、草稿提交協調、歷史、編譯／保存／同步的原因與結果 | 重寫節點運算、直接操作 DOM、將 TD 即時值冒充圖預設 |
| 前端 Adapter | 將核心資料投影成框架資料，將手勢轉成既有操作；按依賴提供更新 | 第二份型別表、節點業務特例、第二份可寫圖、通用「重畫全部」命令 |
| React／React Flow | 控制項生命週期、局部草稿、呈現、量測、視口與拖曳／接線命中 | shader 接線合法性、圖持久化、產品級歷史與同步權威 |
| TD 宿主／Adapter | 身分、原生參數與保護、接收／保存完整圖與前端產物、GPU／預覽 | 前端節點推導、瀏覽器 UI 或 Python compiler fallback |

這是責任表，**不要求每列新增套件、class、事件匯流排或一個轉送服務**。以少量可測 Interface 隱藏真正的複雜度；已有入口合適就重用。正式狀態管理是否使用 Zustand、資料夾名稱與建置配置，由實作者根據需要決定，不能默認等於把圖權威交給 React Flow。

## 5. 「核心先準備好」的具體內容

「完備」以本階段明確涵蓋的產品能力及其操作閉環判定；不是先設計完一切未來功能，也不能只準備一份展示用節點清單。RF-1 必須區分現有能力整理、已在重構範圍內但尚未遷移的能力、另待產品決策的能力。

### 5.1 節點能力與呈現 Interface

- 沿用一份節點定義，讓查詢接孔、可用設定、命令與顯示描述都能在無 DOM 的測試中取得。
- 正式選单從模組明確提供的能力取得；評估版逐個 configure 探測選項僅是查缺口的證據，不照搬成 renderer 的日常工作。
- Title、Body、接孔、值欄位、提示及特殊內容使用共用能力描述。預設排列與樣式合理；普通節點不用重複寫尺寸或完整排版。
- 顯示项以穩定 key／port key／command identity 定位，文字是內容，不當身分。每個欄位的資料讀取與命令寫入對應需明確。
- 同一型別的呈現意圖不改變型別規則。Color RGBA 的整體輸出仍是 vec4，預設沿用 vec4 接孔／線色；有明確覆寫才影響指定部位。RGBA 分量標記、Title、型別文字、接孔與線分開定義作用範圍。
- 正式線與臨時線共用線條樣式解析，臨時狀態可選較細虛線；錯誤、選取等狀態的優先順序集中。評估用色票不成為正式產品預設。
- 真正需要新能力才擴充共用契約；新可選欄位不能要求所有舊節點跟著修改。TextBlock、Body 自由排列及大小設定的精確 schema 仍待整理，不能把先前示意碼視為已批准欄位。

### 5.2 編輯操作、狀態與歷史

前端必須能透過一致入口完成建立／刪除／配置節點、編輯值、連接／替換／取消、移動、動態接孔與既有子圖操作。命令須交代作用目標、成功結果、變更資訊、診斷及失敗是否改動資料；真正提交時重新驗證，不能以 hover 可連接當作永久許可。

一個手勢的局部草稿、正式提交、取消與 Undo 歸屬明確。框架操作暫態與作品狀態分開；歷史依現有圖／宿主責任協調，不能直接複製評估版的整圖快照 Undo 作正式完成。多處顯示引用同一資料來源；取消、外部更新與過期回覆不得覆寫別處的新值。

共用編輯能力如複製、刪除、選取，不逐顆寫入節點。Uniform 即時編輯與常數提交仍是不同操作語意；此階段盤點接入點，不提前恢復被延後的 live channel。

### 5.3 更新、依賴與交付

- 以既有 GraphChanges 為起點，查清節點值、介面、結構、位置、宣告／子圖定義與全域內容的變更含義；必要時補足，避免新造第二套圖 diff。
- 核心提供「改了哪些資料」，不提供「重畫 Source 面板」。前端 Adapter 負責訂閱與投影，未變項目保留穩定引用；不因更新一個值重新產生全部顯示物件。
- 資料更新、React render、DOM 寫入、Layout、Paint 與線幾何分開看；節點尺寸／接孔改變需要幾何更新，純值更新不應直接命令整批畫線。
- 圖變更是否需要產碼、產物交付、保存或只更新畫面，由各責任判定。拖曳、縮放與選取不應平白觸發 shader 編譯／傳輸。不得藉此擅改已約定的保存與同步時機。
- 保留作品／scope／節點／接孔身分及操作版本，讓失敗和晚回覆能對應正確目標；不以 TD 路徑或顯示名稱取代穩定身分。
- 同一份作品快照的圖、GLSL 與綁定描述應能一致交付；宿主接收與原生保護沿用現有清楚入口。前端框架不成為交付契約的一部分。

### 5.4 增加與減少的準則

| 應增加／補足 | 應減少／淘汰 |
| --- | --- |
| 真正缺少的節點能力查詢、顯示描述、操作結果與診斷 | renderer 按節點名稱／UUID 猜特例 |
| 有證據需要的變更通知、讀取投影與訂閱 | 同一值多份權威、各區自己掃描整圖 |
| 控制項與樣式的共同規則、清楚的預設與可選覆寫 | 為單顆節點複製控制項／CSS 或重寫型別規則 |
| 必要的應用層歷史、取消、宿主交付 Interface | 搬運整份舊 app／runtime、永遠保留雙寫／fallback |
| 針對實際依賴的測試與可見診斷 | 為未知未來能力先堆空殼、為過關建立假產品路徑 |

保留已經有效的模組，不因框架選擇重寫核心。每個過渡 Adapter 都需列明依赖它的入口與移除條件。

## 6. 分階段順序與進度

這是一條集中的主線，先完善核心／應用 Interface，再接新畫布；不在舊 UI 各處散落微調後宣稱完成解耦。下列狀態分開描述人類方向、計畫與實作。

| ID | 階段／順序 | 可交付成果及完成條件 | 目前狀態 |
| --- | --- | --- | --- |
| RF-0 | 收斂評估、建立計畫 | 記錄 React／React Flow 方向、原型位置、核心價值、後續 Interface 與驗收；原型不转正 | **本輪文件完成**；方向已獲人類認可 |
| RF-1 | 核心與應用能力盤點 | 在本文件補逐項能力表：單一來源、現有入口、缺口、依賴、保留／補足／淘汰及驗收；定義第一個正式節點交付範圍 | 待實作；下一個工作起點 |
| RF-2 | 完善節點／圖的核心契約 | 沿既有模組完成 5.1／5.3 必要能力，拿真實節點驗證設定、命令、接孔、呈現與產碼一致；完成所選範圍的能力缺口 | 待實作；不得只有型別宣告或假模組 |
| RF-3 | 整理應用操作與資料交付 | 同一作品與命令入口、草稿／提交／取消、歷史、變更發布與產物交付 Interface 可在無 renderer 情況測試；分離舊 app 全域相依 | 待實作；與 RF-2 依真實依賴迭代，不先建空框架 |
| RF-4 | 正式新前端：節點與畫布 | 新產品入口用 React／React Flow 接上述 Interface；涵蓋節點 Title／Body、控制項、線、幾何、操作與必要歷史；同一 DOM／可變屬性只由一套機制管理 | 待實作；不直接搬評估版、尚未換正式入口 |
| RF-5 | 面板討論與遷移 | 人類討論後補責任／資料引用／操作入口／遷移表；再依相依接 Source、Parameter、Help、工具列及其他面板 | **待後續討論**；本輪不定排版、詳規與順序 |
| RF-6 | 完整產品接入、移除過渡、交付 | 按能力表補完尚未接入範圍，真實宿主／保存／歷史／效能驗收，移除被替代路徑並更新版本／交付記錄 | 待實作；不以節點畫布通過代替全產品完成 |

**RF-1 的盤點至少包含兩種層級：**

- 共用能力：節點顯示描述、值編輯、型別配置、接孔動態、接線規劃、交易／歷史、變更發布、子圖 scope、產碼與宿主交付。
- 產品能力群：已遷移 numeric／logic／vector／Uniform／TOP Output／子圖；尚未完成的自訂 GLSL、Texture／Sampler／TOP Input、array／struct／matrix、MAT／Vertex 與特殊 editor 節點。各自標明核心、應用、宿主、UI 哪些已完成；ISF 等其餘範圍沿既有產品計畫追蹤。

第一個正式交付範圍建議從已遷移 TOP 節點群及代表性動態／子圖案例開始；**這是工程建議，不是刪減剩餘能力**。整理的是能支援完整產品的共同 Interface，不等待所有尚未定案功能做完才驗證接入，也不把缺口藏在「可新增清單」之外。RF-1 若查到某能力必須先補才能成立，就明列前置，不以 Legacy fallback 硬通過。

每段在同一張能力表補程式入口、測試、commit、剩餘範圍與退回方式。既有 STATUS 只摘要交付位置，不另起平行進度表。舊 UI-0 已完成的是前版文件；UI-1 的隔離實驗歸為本輪證據；舊 UI-2「先接 Uniform 三處顯示」不再是固定第一步，其驗收要求留到相應能力接管時。

## 7. 中途驗證怎麼安排

**先定不變的驗收問題，再選測試入口。** 人類尚未決定中途以新入口、舊入口或混合方式試用；以下是推薦分工，不把舊 UI 支援變成新核心必須永遠背負的成本。

| 階段／對象 | 建議驗證入口 | 能證明與不能證明的事 |
| --- | --- | --- |
| 核心契約與節點能力 | 無 DOM、無 TD 的真實模組／圖／產碼測試；沿用既有 test:core | 證明規則與操作；不能當作 UI 可用或 TD GPU 通過 |
| 顯示契約與前端 Adapter | 隔離的新正式節點入口；評估版作參照 | 證明同一核心能被新 UI 使用；不靠改舊 renderer 才完成核心測試 |
| 舊行為對照 | 固定 Legacy／目前 Refactor.14 的適用操作及已有證據 | 比對能力與 UX；不要求保留舊資料格式、舊 protocol 或 DOM 組織 |
| 宿主與保存 | 明確識別版本、目標及程序的隔離 TD | 驗證前端產物、原生參數、Undo、失敗回退、保存重開與無 Manager 使用 |
| 面板／跨區互動 | RF-5 討論後選定入口 | 焦點、草稿、多處引用、選取及歷史協調；本輪不為測試先蓋假產品面板 |

開工前先確認第一個交付範圍與人類試用入口；具體底層測試方法由實作者決定，不逐項要求人類選工具。採舊入口過渡時列出 Adapter 與退出條件；不建立兩份互相同步的可寫圖，也不讓新舊 renderer 共同修改同一 DOM。

### 必須能回答的驗收問題

1. **節點只定義一次嗎？** 加一個使用既有能力的節點，只修改其定義／正常註冊；UI、型別及 compiler 不新增名稱分支。
2. **一個行為只由一處決定嗎？** 相同值的多個控制項使用同一資料來源與命令；樣式改一處，各引用一致，未指定部位不被染色。
3. **核心真的能獨立嗎？** 刪去測試用 React renderer 後，核心節點編輯、接線、配置與產碼案例照常成立；反向也不要求 UI 自行計算合法型別。
4. **不相關的東西保留嗎？** 修改值不丟其他欄位草稿／焦點，不主動重建無關面板與線；有真實尺寸或介面改變時，相關幾何正確更新。
5. **操作與資料可靠嗎？** 拖曳／接線取消無殘留，一個手勢按既有語意進歷史；Undo／Redo 保持圖與宿主責任。晚回覆、刪除、切圖及外部改值不覆寫新狀態。
6. **產品仍完整嗎？** 已涵蓋範圍有真正可用的完整流程；未涵蓋清楚回報及保留內容，不能用缺失節點／測試 fixture 冒充功能交付。
7. **時間花在哪裡？** 分開模型／投影、React commit／DOM／Layout／Paint、GLSL、傳輸及 TD apply；小圖與約 100 線代表圖量測絕對 ms、波動與較慢樣本，不把原型 FPS 視為所有裝置的保證。
8. **閒置與退出乾淨嗎？** 切圖、關面板、斷開或沒有編輯者後，訂閱與手勢清理；沒有新增 TD 待機掃描、預覽或診斷刷新。

效能門檻依代表圖、既有證據與所改路徑訂定；不憑空許諾每條線多少 ms，不為無實際影響的微小差額延誤產品。其他瀏覽器、弱裝置、觸控、真實宿主未測就明確標示；測試失敗先辨認既存或新退化。

## 8. 面板留到後續討論

本輪只確定：面板是明確的 Module，讀取所需資料、提供自己的操作，不直接刷新其他面板或 Canvas。節點模組描述節點內容，不掌管整個 Parameter／Source 面板；值編輯等共同能力應重用，而非每個面板重新發明。

到 RF-5 再討論：

- 各面板提供哪些產品功能，哪些資料為唯一來源，哪些是選取／折疊／搜尋等本地狀態。
- 節點 Inspector、Source、TD 原生 Parameter、Help 與工具列的命令、訂閱及責任如何分配。
- 停駐／浮動、版面配置、跨面板草稿／焦點與快捷鍵如何保留，以及實際接管次序。
- 哪些現有面板能力可直接重用、需要重寫，或尚未遷移。

此清單是下次對話的題目，**不是已決定重做全部面板或預設某種版面**。不以等待面板詳規阻擋已明確的節點核心整理。

## 9. 範圍、风险與退回

未因這次計畫自動轉正：Uniform live channel 恢復、HTTP／WebSocket／WebRTC 改造、GLSL 與圖分流、JSON Patch、同步／綁定權威變更、完整離線 Sketch、PWA、Library 更新／Portable Library、動態 TS 節點安裝、多 Buffer、矩陣候選 A／B、Auto、轉換規則擴大與脫皮。它們仍依既有待辦與產品決策安排；其中屬最終產品必要能力者不因延後而刪除。

主要風險與處理：

- **新框架透過投影又引入全量刷新：** 檢查訂閱、參考穩定性与正式提交頻率；用真實變更案例定位，不能只看 React render 次數。
- **為適應舊 UI 留下過多相容包袱：** 逐一列明舊入口用途；接管後移除相應分支，核心不依賴相容投影。
- **原型捷徑被當產品規格：** 對每個帶入能力核對契約、權威與完整操作；不整包複製探測、簡化歷史、樣式色票或阻尼轉接。
- **資料或宿主狀態受損：** 每段保留可退回提交與必要資料副本；同一圖只走一條正式写入路徑。來源退回不等於宿主／資料自動復原，後兩者須有相應策略。
- **架構整理變成無止境工程：** 以真正產品案例界定完成；沒有使用者需求或現有缺口支持的抽象先不加。待討論只阻擋依賴它的部分。

沿既有流程進行本地 refactor commit；版號前進時提交該版本完整可用所需內容，不推送 main、不擅自發布。遇到產品行為、資料權威或既定範圍衝突，帶具體反例回報；普通技術選擇及修錯由實作者完成。
