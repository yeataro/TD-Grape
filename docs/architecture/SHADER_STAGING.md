# Shader 發布保護：單節點、候選驗證與 A/B — 設計評估

2026-09-09。使用者提議兩份 GLSL MAT 或兩份 GLSL TOP：一份工作，一份檢查。此文件是研究結論與待測項，不代表 0.2 已改為 A/B。

## 2026-09-09 實機逐幀結果：本版保留臨時候選

本機 TD 2025.32820，64 × 64，逐應用程式幀修改 vec4 Uniform、強制 render 並讀取中央 6 × 6 像素。原生方案跑兩次各 200 幀：第二次先啟用 threadedprevious/showprevious，再經過 20 幀正常輸出才注入錯誤，排除只在失敗時切換模式的影響。兩次結論一致。

- MAT：60 幀語法錯誤期間輸出維持失敗前的 Uniform 值，不再隨新值改變；其中 3 幀數值偶然匹配循環輸入，不代表持續更新。本測試不能單獨區分凍結影像與保留 Shader 但 Uniform 停止更新，兩者均不符合本產品需求。
- TOP：同一段 60 幀語法錯誤全部仍符合動態 Uniform 的預期值。但把唯一綁定從 uProbe 改成 uRenamed 後，60 幀全部不符合舊版預期；保留 Shader 不會替我們保留完整綁定設定。
- 恢復程式及綁定後，兩種類型的 30 幀全部正常。基準幀也全部符合預期，誤差容許值 0.012（包含 8-bit 量化）。
- TD 診斷陷阱：MAT Info DAT 可以同時包含 Pixel compile ERROR 與 Linked Successfully；背景編譯首幀也可能暫時保留前次成功訊息。TOP 在 showprevious 時 errors() 可為空，但 Info DAT 明確有 compile ERROR。不可只用單一成功字串或空 errors() 判定背景候選已通過。
- 現有同步臨時候選流程另跑 100 幀：同時改名 Uniform、把白色 sampler 改為黑色並在 TD 注入語法錯誤，被候選驗證拒絕；另注入正式提交失敗，回復 Graph 與綁定。100 幀輸出全部仍符合當幀動態 Uniform，正式示範維持 revision 20、程式與參數不變。

**本版決策：保留現有同步、按需建立並清除的候選 MAT。** 原生單節點尚未通過必要的動態保護條件，已有具體理由保留候選；目前沒有證據支持增加常駐 A/B。TOP 只作原生能力對照，沒有新增 Sgrape TOP 產品功能。

限制：量測發生在每個應用程式幀回呼的操作完成後，不證明 configure 內任意觀察點具有原子性；未作 GPU 效能基準、冷啟動失敗恢復或所有燈光變體測試。報告中的 readbackWallMs 含 Python、cook 及讀回，不是 GPU 時間。後续若改寫發布策略，仍須依下列完整驗收重新確認。

證據：reports/native-shader-probe-initial.json、native-shader-probe.json、candidate-protection-probe.json。維護腳本為 tools/jobs/test_native_shader_probe.py、test_native_shader_probe_callbacks.py、test_candidate_protection.py、test_candidate_protection_callbacks.py；需透過已授權 TD bridge 執行，完成後清理自身 fixture。

## 原設計與完整驗收：單節點優先，候選按必要性決定

使用者再次要求謹慎評估兩份 GLSL TOP／MAT 是否有必要。固定需求是「失敗版本不影響正式輸出」，不是兩個常駐節點。將候選版本與最後成功版本分成兩份資料狀態，不等於一定要兩個 GLSL operator；符合相同驗收條件時，優先選擇較簡單的實作。

### 驗證權威與額外節點的取捨

使用者確認：最終編譯與連結的依據是 TD 本身的實際結果。我們的圖結構、型別與程式產生檢查可以提前提示問題，但不取代 TD 在實際目標與環境下的驗證。

額外的候選 GLSL 節點是取得驗證與保護正式輸出的手段，其存在本身不是要求。若單節點配合 TD 原生能力能通過相同驗收，就省去額外節點；若候選節點提供不可取代的隔離或驗證能力，就保留。精簡不得降低驗證可信度，也不為減少節點數而犧牲輸出穩定性。

### 本機實證與文件差異

2026-09-09 只讀檢查本機 TouchDesigner **2025.32820** 的 `/project1/Sgrape_MAT1/material`：

- `compilebehavior` 確實提供 `threadedprevious`，目前仍設為 `stalluntildone`。
- `errorbehavior` 確實提供 `showprevious`，目前仍設為 `showcheckerboard`。
- 正式元件沒有錯誤；檢查時沒有候選節點，符合現況「部署時臨時建立、完成後清除」。

GLSL TOP 官方文件列出這兩組選項；GLSL MAT 的線上與隨附離線說明沒有完整列出，但實機有提供。因此不能用文件缺項判定 MAT 不支援。這次只確認參數能力，沒有修改正式 MAT 設定，也尚未測出切換模式後的完整失敗行為。證據另存為本工作資料夾的 `shader-publication-capabilities.json`。

### 依修改內容選擇驗證範圍

| 修改內容 | 最小可行方向 | 目前證據與限制 |
| --- | --- | --- |
| Exposed Uniform 目前值 | 直接更新現有參數 | 0.2.1 已實作，沒有重寫 Shader 或建立候選。 |
| 只移動節點等不改編譯結果的操作 | 只更新 Graph 資料 | 既有 deploy 以編譯 hash 跳過材質配置；不用額外 GLSL operator。 |
| 改程式，Uniform／sampler 介面與其他設定不變 | 優先研究單一 GLSL operator 的保留前一份 Shader 模式 | 原生選項存在，但須證明舊 Shader 持續運算、能辨認新編譯真正完成，並正確處理快速連續修改。 |
| 改 Uniform 名稱／型別／Expose、sampler、輸入或輸出設定 | 先分離待發布設定，檢查單節點能否整組安全套用 | 保留前一份 Shader 不等於保留所有 TD 參數、資源綁定或輸出配置；若會干擾舊版，才採用獨立候選。 |

這是依程式與參數能力作出的設計推論，不是已驗證的執行策略。為降低實作複雜度，未必需要按每種修改建立多條發布路徑；先比較一套簡單策略能否滿足所有已支援操作，再決定是否值得區分。

### 單節點必須證明的事項

1. 語法／連結失敗及背景編譯期間，動態 Uniform 與貼圖仍驅動最後成功 Shader；逐幀確認沒有錯誤影像，且不是凍結一張舊圖。
2. 新版的參數或 sampler 配置不能提早改壞正在使用舊版 Shader 的輸出。例：舊程式還讀取 `uTint`，新版失敗時不可已將唯一的綁定名稱改成 `uColor`。需覆蓋改名、改型別、移除、貼圖替換與缺失等情況。
3. 必須分辨「仍顯示舊版」和「候選新版已成功」。不能直接沿用目前 `validate_material()` 的立即 cook 加上 `Linked Successfully` 字串，就假定非同步候選完成；需找出並實測與候選 revision 對應的完成／錯誤訊號。
4. 編譯失敗後保存並重開，應先從最後成功版本建立有效輸出，失敗草稿另存；不能依賴重開後未必存在的 GPU 快取。
5. 在同一場景、解析度及 viewer 條件下比較幀時間、cook 與記憶體。只有雙節點帶來必要的隔離或可測的改善，才接受其额外資源、切換與維護成本。

### 對目前實作的保守結論

0.2.1 先驗證臨時候選，再逐項配置正式 material；若正式提交出错則回填上次內容。`configure()` 會依序修改公開參數、Shader DAT、sampler 及 Uniform 綁定，這不是可證明所有中途觀察都不可見的原子切換。現有測試證明了最終狀態與既有 Expression 等可復原，尚未證明所有失敗點都逐幀沒有短暫異常。這個限制要如實保留，也不能因有候選就稱為零風險。

**後續順序：優先驗證單節點的原生保留能力與設定一致性；通過相同驗收就採用單節點。只有單節點無法滿足必要條件，或雙節點有可量測的合理收益，才選臨時／重用候選或 A/B。TOP 與 MAT 各自驗證，不為外觀一致而強迫同一實作。** 本次不變更已交付功能，不承諾任何方案零風險。

## 可選方案：獨立候選與 A/B

若單節點無法滿足發布保護，才考慮保留「最後成功」A；只對 B 寫入候選程式、介面、Uniform / sampler 設定。編譯／連結與代表場景驗證成功，再切換對外入口；失敗只保留錯誤草稿，A 繼續工作。兩份應使用同類 Shader 與相符的環境，GLSL TOP 不能代替 GLSL MAT 的幾何、燈光與 TD builtins 驗證。

目前 0.2 已先建立臨時候選場景並驗證，再配置固定的正式 material；提交失敗重新配置前次內容。每次成功涉及候選和正式两次配置／驗證；不等於硬體必定完整編譯兩次，快取命中與場景變體會影響結果。暫時候選在部署結束後清除，沒有常駐第二套渲染。

可先量測固定重用候選是否減少元件建立成本；再評估 A/B 直接切換是否避免正式端第二次配置。MAT 可研究固定 Select MAT 對外入口，內部選 A 或 B；需確認它的材質／Deform / Common 設定與現有 GLSL MAT 引用完全相容。TOP 可研究固定輸出選擇，但未選路徑不能被 viewer、預覽讀取或其他使用者持續要求 cook。

## 成本分開看

- 編譯：結構、型別、程式內容改变需要新 Shader；純 Uniform 值一般只需更新資料。已曝露的 TD 參數已有直接绑定路徑。檢查端成功後再重寫正式端仍可能有額外編譯／pipeline建立，不能宣稱零成本。
- 每幀 GPU：兩個節點存在不等於兩次完整渲染。備用只按需驗證、未參與輸出，才可能避免持續增加繪製工作；要以 cook 計數與 GPU 時間确认。
- 記憶體：兩份程式／pipeline 與狀態會多占空間；TOP 另可能保留輸出紋理。例如單張 3840×2160 RGBA16F 約 63.3 MiB，不含其他緩衝、mipmap、對齊和驅動資源。驗證用 Render TOP 也需計入。
- 卡頓：同步編譯仍可能阻塞主執行緒，雙節點本身不能消除。GLSL TOP 的 Compile Behavior 有背景編譯保留前一份、Error Behavior 有保留前一份，但不會自動替我們保證整份 Graph 與公開參數狀態的交易一致性。
- 驗證範圍：MAT 會因渲染情境（例如燈光排列）產生變體；一個測試場景編譯成功不代表所有可能場景都已預熱。

## 下一步驗收

比較單節點原生保留、現況臨時候選、固定候選重用、固定入口 A/B 四種策略：冷／暖啟動、簡單／複雜圖、快速連續編修、僅改 Uniform、故意編譯失敗與參數介面變更。记录 CPU wall time、最大幀時間、GPU 時間、cook 數量與 GPU 記憶體，保持解析度、場景與 viewer 條件一致。GPU 計時不可只拿 Python 呼叫時長替代。

成功條件包含：失敗時舊 Shader 繼續運算而非只留靜止截圖；對外材質路徑不變；TD Expression / Bind 不斷；儲存重開保留有效版本；候選 viewer 不造成每幀額外渲染。背景編譯需要明確完成狀態，不能把「仍顯示舊 Shader」當成新版本驗證成功。

先保持 0.2 已驗證的提交策略，把性能變更放在下一個可回歸驗證的版本。此方案保護編譯／提交失敗，不是隔離 GPU hang 或任意 Shader 的程序崩潰。

## 補充：驗證通過才發布

使用者澄清：核心要求是錯誤版本不得進入正式輸出，不指定必須有兩個常駐節點。允許按需啟用驗證、候選重用、A/B 切換或回退；以穩定和實際性能選擇。

把流程分為「編修／驗證」與「正式輸出」兩個邏輯階段。正式輸出只引用最後成功版本，繼續接收正常的時間、貼圖及可相容的 Uniform 更新。正在編修的程式、介面或資源配置留在候選側。

驗證端只在內容有新版本時工作。沒有新修改時，不應因預覽、viewer 或輪詢持續渲染備用場景；採用哪一個 TD 開關要按元件類型確認，不能假定所有 GLSL 節點都有同一個 Active 參數。

發布條件必須包含新版本已完成編譯／連結、必要的實際場景驗證、資源及參數綁定有效，而且驗證結果仍對應最新候選版本。編譯中或失敗時，正式輸出保持原版；錯誤只顯示在編輯器。失敗後的草稿保留供修正，不覆寫最後成功的 Graph／材質狀態。

回退是提交失敗的額外保護；不能把「先讓錯誤版本進入輸出、發現後再回退」當成符合此要求。若研究單一 GLSL 節點配合 TD 保留前一份 Shader，仍須驗證失敗的程式和參數變更沒有影響目前輸出。

新增驗收：在動態貼圖／動畫 Uniform 持續變動時故意輸入編譯錯誤，逐幀檢查輸出仍由最後成功 Shader 產生；不可閃現錯誤棋盤、黑畫面或其他候選錯誤影像，也不可只凍結一張舊圖。另驗證快速連續修改時舊候選完成不能覆蓋最新候選，以及閒置驗證端不持續 cook。

0.2 既有候選驗證及提交失敗復原已通過原有測試；以上動態逐幀不中斷、閒置 cook 與不同發布策略的比較是後續新增驗收，尚未宣稱通過。
